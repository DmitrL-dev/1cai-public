# Рентген Core 0.1.0.dev10 — HTTPS-приём уведомлений

Предварительный выпуск для Windows x64 / CPython 3.11. Он добавляет проверенную
локальную HTTP/HTTPS-границу к ранее выпущенному долговечному приёмнику
уведомлений. Ранее опубликованный core dev9 и его байты не меняются.

## Для пользователя

- `NotificationReceiverASGI` принимает уведомление от существующего
  `WebhookAdapter` по точному маршруту `POST /notifications`. Сначала успешно
  открывается и проверяется принадлежащая хосту SQLite-база; только затем
  сервер начинает обслуживать запросы.
- Bearer-токен, ключ идемпотентности, JSON и его канонический digest
  проверяются уже существующим `NotificationReceiver`. Первая доставка
  сохраняет квитанцию и возвращает HTTP 204. Повтор того же ключа с тем же
  содержимым также даёт 204 без второй записи; другое содержимое с тем же
  ключом даёт 409.
- На HTTP-границе отклоняются неподходящий метод и маршрут, не-HTTPS схема,
  дубли заголовков, которые дошли до ASGI, недопустимый Content-Length,
  Transfer-Encoding, незавершённое или слишком большое тело. При потере
  соединения до полного тела квитанция не создаётся. Ошибки хранилища и
  неожиданные внутренние ошибки дают фиксированный пустой 503 без токена,
  тела запроса или пути базы в ответе.
- Базовый wheel остаётся без обязательных сторонних runtime-зависимостей.
  Приложение экспортируется как `rentgen_core.NotificationReceiverASGI`;
  отдельный ASGI-хост поставляет сокет, TLS и управление процессом.

## Проверенный локальный путь

Для проверки использованы Uvicorn `0.52.4` и `httptools==0.8.0` с явным
`http="httptools"`, прямым TLS и выключенными proxy headers/access log.
`WebhookAdapter` отправил запрос по TLS с проверкой временного сертификата,
приёмник записал одну квитанцию, после перезапуска ответил на повтор 204 без
новой строки. Недоверенный сертификат и обычный HTTP не создали квитанцию.
Отдельные сырые TLS-запросы с повторным, объединённым и неканоническим
Content-Length, а также двойной Authorization дали 400 до записи.

Выбор HTTP-парсера существенен: Uvicorn/h11 может объединить одинаковые
Content-Length до передачи заголовков ASGI-приложению. Поэтому `http="auto"`
и `h11` не входят в проверенную конфигурацию этого контракта. Другой парсер
или хост требует собственной проверки на уровне wire. Хост также отвечает
за ограничения времени чтения и конкурентности.

## Границы предварительного выпуска

Приёмник сохраняет **только digest receipt**, не восстановимое событие и не
результат бизнес-обработки. Ровно однократная бизнес-обработка не заявляется.
Этот тест не разворачивает публичный адрес или Windows-службу и не принимает
настройки DNS, сертификатов, секретов, доступа извне, восстановления после
обесточивания или враждебной конкурентной замены файлов. Типовые конфигурации
1С и живая информационная база не были приняты в этом выпуске. Production
deployment требует отдельного глубокого ревью и разрешения владельца.

Подробный контракт и примеры: [NOTIFICATION-RECEIVER.md](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/product/NOTIFICATION-RECEIVER.md).
Крупная [схема работы Рентгена](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/assets/how-rentgen-works.svg)
показывает путь от выгрузки 1С до решения о правке.
