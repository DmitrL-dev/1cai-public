# Рентген Core 0.1.0.dev12 — причина отказа Git-аудита в локальном журнале

Предварительный выпуск для Windows x64 и CPython 3.11. Новый диагностический
контракт помогает разбирать отказ BSL-анализа после завершения обычного
процесса службы. Опубликованные файлы, теги и контрольные суммы dev11 сохраняются.

## Что изменилось

Раньше BSL-адаптер знал причину отказа, но Git-аудит оставлял только общий
`GIT_ANALYZER_INCOMPLETE`. Теперь проверенный код причины сохраняется в
`profile/git-journal.json`:

```json
{
  "status": "fatal",
  "code": "GIT_ANALYZER_INCOMPLETE",
  "analysis_failure": {
    "schema": 1,
    "reason": "BSL_RUNTIME_MISMATCH"
  }
}
```

Это пример отказа при несовпадении runtime. Причина появляется только после
проверки полного ответа адаптера и его привязки к анализируемым байтам.
Неизвестный или недостоверный ответ сохраняет прежнюю общую ошибку.

Перед записью проверяются точный тип ответа, статус, хэш и размер исходника,
профиль, манифест и конфигурация. Доступ повторно проверяется после анализа:
отозванное разрешение имеет приоритет над диагностикой. Допустимы только 15
фиксированных кодов адаптера и их варианты с одним суффиксом ошибки очистки.
Похожая строка в обычном исключении не может создать такую запись.

Внешний CLI по-прежнему возвращает `SERVICE_WORKER_FAILED`; уведомление outbox
содержит общий `GIT_ANALYZER_INCOMPLETE`. Новая причина не попадает в транспортную
сериализацию ошибки. Пути файлов, исходный BSL, principal, stdout/stderr и текст
исключения в новое поле не копируются. Проверки целостности runtime, изоляция,
очистка, повторные попытки и критерии успешного отчёта не ослаблены.

## Как пользоваться

1. Установите проверенный комплект dev12 по
   [инструкции](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/product/CORE-INSTALLATION.md).
2. Если обычный Git-аудит завершился ошибкой, откройте `git-journal.json` в
   каталоге его профиля. Записи `run_id`, `cycle`, `updated_at` помогают связать
   событие с конкретным запуском.
3. Скопируйте журнал до перезапуска: он хранит текущее состояние и будет заменён
   новым запуском. Отдельный архив ошибок этим выпуском не добавляется.
4. Сверьте `analysis_failure.reason` с
   [описанием службы](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/product/SERVICE-HOST.md).
   Отсутствие поля означает, что проверенной дополнительной причины нет.

Миграция профиля для нового поля не требуется. Для редактора подготовлена отдельная
совместимая версия Companion 0.1.12; выбор нового Python в профиле выполняется
явно. Уже созданные профили сохраняют прежнюю версию ядра.

### Ограниченная нативная проверка Git-аудита

В отдельной установке изменён один байт собственной копии JAR при сохранении
размера. Обычный установленный service CLI вернул exit 2; journal сохранил
точный `BSL_RUNTIME_MISMATCH`, внешний JSON и outbox остались общими,
owner reports отсутствовали. Отказ проверки хэша произошёл до запуска Java.
На другом новом синтетическом проекте штатный service CLI завершил один цикл
с exit 0 и реальным `bsl/MagicNumber`; owner report связан с проектом, снимком
и коммитом и имеет provenance `git_source_verified`. Исходники сохранились
побайтно, включая исходные CRLF.

Эти native-опыты выполнены на локальном комплекте. Все 103 файла установленных
пакетов совпали с wheel и исходным коммитом; тот же wheel и scanner побайтно
совпали с принятым CI-комплектом. Отдельная офлайн-установка CI ZIP проверена
дополнительно. [Протокол всех трёх опытов](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/product/SERVICE-GIT-FAILURE-REASON-DEV12.md)
сохраняет и неудачную первую установку; он не является приёмкой надёжности
холодного старта или службы Windows SCM.

Узкие локальные проверки новой диагностики: 141 тест; совместимости и поставки:
47 Python-тестов; Companion: 63 Node-контракта. Дополнительно прошли 38 тестов live apply/recovery. До реализации новый тест
воспроизвёл потерю причины. Проверены подмена привязки и типов, неизвестные
строки, отзыв доступа, отсутствие причины в outbox и сериализации, сохранение
первичной ошибки при сбое записи и замена журнала следующим запуском.
Контрактная проверка отдельного процесса использует управляемый watcher;
управляемый адаптер проверяется отдельно в композиции сервиса. Эти тесты
не объявляются нативной репродукцией прежнего runtime-сбоя.

## Известное ограничение холодной установки

В ходе проверки dev12 первая новая установка снова остановилась с
`BSL_INPUT_CHANGED` при проверке подготовленного каталога JDK, до запуска
службы. Неудачный staging и stderr сохранены. Позднейшие успешные проверки
не отменяют этот результат. [Issue #23](https://github.com/DmitrL-dev/1cai-public/issues/23)
остаётся открытым: этот выпуск добавляет диагностику будущих отказов worker,
но не исправляет перемежающийся отказ установщика и не устанавливает причину
старого публичного прогона №14.

Полная приёмка Windows SCM, типовых `.cf/.cfe`, живой рабочей ИБ и внешнего
конкурентного изменения исходников этим выпуском не заявляется. Исторические
проверки на платформе 1С для dev11 не считаются проверками новых байтов dev12.
Production deployment требует отдельного ревью и разрешения владельца.

[Большая цветная схема работы Рентгена](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/assets/how-rentgen-works.svg)
показывает путь от выгрузки 1С до проверки и решения о правке.
