# Рентген Core 0.1.0.dev13 — проверка каталогов и прав Windows без ложных отказов

Предварительный выпуск для Windows x64 и CPython 3.11. Исправлен конкретный
механизм ложного `BSL_INPUT_CHANGED` при проверке BSL runtime и сравнение
строковых представлений прав каталога, вызывавшее `BSL_PROCESS_FAILED`. Этот выпуск
продолжает расследование [issue #23](https://github.com/DmitrL-dev/1cai-public/issues/23).

## Что изменилось для пользователя

Проверка могла отвергнуть неизменённый каталог после его повторного открытия
только для чтения. Windows обновляла сохранённые в родительском каталоге
сведения о времени дочернего каталога. Рентген сравнивал эти сведения как
изменение самого дерева, хотя файлы и метаданные уже открытых объектов
сохранялись.

Теперь полные метаданные каталога читаются через удерживаемый дескриптор
этого объекта. При повторной проверке Рентген читает их заново, поэтому
настоящее изменение продолжает вызывать отказ. Список имён, идентификаторы,
тип объекта, атрибуты, время создания и окончательный путь также проверяются.
Проверки содержимого файлов, SHA-256, hardlinks и reparse points сохраняются.

Изменение находится в 18 строках `RuntimePins._inventory` и применяется там,
где этот механизм используется для runtime, исходников и принадлежащей
процессу попытки BSL-анализа. Лимиты 1080 handles, 1024 элементов inventory
и 512 MiB учитываемых файлов не увеличены. Повторных попыток, задержек перед
проверкой и подавления обнаруженных изменений не добавлено.

Локальная диагностика причины отказа из dev12 сохранена. При отказе обычного
Git-аудита проверенный `analysis_failure.reason` находится в `git-journal.json`
профиля. Журнал нужно сохранить до следующего запуска, который заменяет его
текущее состояние. Внешний CLI и outbox продолжают возвращать общие коды.

## Права служебных каталогов: числовой SID и сокращение LA

При первых полных CI новый тест OwnedAttempt выявил отдельный дефект.
CreateDirectoryW успешно создавал каталог, но прочитанная строка DACL
содержала `LA` для встроенного локального администратора, а ожидаемая —
полный SID того же пользователя с RID 500. Строгое текстовое сравнение
ошибочно отклоняло совпадающую политику.

В диагностических CI `36295050972` и `36295054030` записаны успешный
результат создания, текущий SID и фактический DACL. Локальная конвертация
descriptor подтвердила переход к LA без изменения ACL или учётных записей.
Первоначальная трактовка этого отказа как неудачи CreateDirectoryW уточнена
в протоколе и публичном отчёте; неуспешные прогоны сохранены.

Теперь ожидаемый и прочитанный descriptor преобразуются одним Windows API
с DACL_SECURITY_INFORMATION. Сравнение сохраняет защиту от наследования,
ACE, trustees, права, flags и порядок. Ожидаемая строка вычисляется до
создания каталога. Ошибка или пустой результат конвертации запрещают
создание; ошибка LocalFree помечает cleanup_uncertain. Ручной подстановки
SID и повторных попыток нет.

Добавлено 15 контрактов. Для SY/LS/NS старое сравнение даёт ожидаемый отказ;
тесты также проверяют обычный SID, восемь реальных изменений политики,
ошибку/пустой результат преобразования и ошибку освобождения памяти.
Service-account варианты используют файловый seam и настоящие Windows
преобразования descriptor. Это не проверка запуска SCM под SYSTEM.

## Установка и совместимость

1. Скачайте комплект dev13 и проверьте его SHA-256 по `SHA256SUMS` и
   `manifest.json` из этого релиза.
2. Установите его в отдельное окружение по
   [инструкции Core](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/product/CORE-INSTALLATION.md).
3. Для редактора используйте Companion 0.1.13. Генератор профиля проверяет
   выбранный установленный Python и записывает фактическую версию ядра.
   Уже созданные профили не переключаются автоматически.
4. При отказе сохраните журнал и сопоставьте его с конкретным запуском.
   Не считайте отсутствие новой причины признаком успешного анализа.

Опубликованные Core dev12, Companion 0.1.12 и их контрольные суммы остаются
доступными. Этот выпуск не меняет формат пользовательского BSL-исходника
и не запускает рабочую информационную базу при установке.

## Как воспроизведена ошибка

На неизменённом установленном dev12 создано собственное дерево из 128 файлов
и 16 дочерних каталогов. После успешной исходной проверки повторное открытие
дочернего каталога только для чтения вызвало `BSL_INPUT_CHANGED`.
Полные stamps удерживаемых каталогов и содержимое файлов совпали до и после.
В отдельном инструментированном опыте сохранена именно неравная пара
перечислений, вызвавшая отказ: изменились только кэшированные write/change.

В исходной исправленной версии прошли 9 наблюдаемых обновлений кэша.
На первоначальном локальном dev13 из `64197b7` этот опыт прошёл с 5 наблюдаемыми
обновлениями: класс и операции не подменялись, все 128 файлов сохранились,
retained stamps остались прежними, собственные handles закрыты. В новом
wheel из `1519d8b` модуль RuntimePins побайтно тот же; изменён только модуль
OwnedAttempt и его запись RECORD. Это проверено по всем 103 файлам пакетов. Опыт без
реально наблюдаемого обновления кэша не засчитывался бы как положительный.

[Исходный протокол и отрицательные контракты](https://github.com/DmitrL-dev/1cai-public/blob/1519d8bbf0c5aabb4e804e88640a98bacff44a93/docs/product/RUNTIME-DIRECTORY-STAMPS.md)
отделяют доказанный механизм от исторических случаев с неполной трассой.
[Публичная запись установленных результатов](https://github.com/DmitrL-dev/1cai-public/issues/23#issuecomment-5852796592)
содержит хэши локальных проверок.

## Проверки установленного кандидата

- Две локальные сборки kit дали одинаковые байты; офлайн-установка с
  проверкой хэшей подтвердила 40 файлов, 30 wheels и 32 CLI/MCP-инструмента.
- Все 103 файла `rentgen_core`, `rentgen_graph`, `rentgen_diagnostics`
  совпали с wheel и Git archive исходного коммита. Архив исходников отдельно
  совпал с повторным `git archive` того же коммита.
- Первая собственная свежая установка runtime и обычный service CLI прошли:
  exit 0, один настоящий `bsl/MagicNumber`, provenance `git_source_verified`.
  Проверены project/snapshot/commit/report bindings и точные UTF-8/CRLF
  исходника. После завершения каталог попыток пуст, `.install-*` отсутствует.
  Дополнительный аудит содержит 27 проверок без расхождений.
- Во второй отдельной установке изменён только первый байт собственной
  копии JAR. CLI завершился с exit 2 и `SERVICE_WORKER_FAILED`; журнал содержит
  точный `BSL_RUNTIME_MISMATCH`, outbox — общий `GIT_ANALYZER_INCOMPLETE`.
  Успешный owner report отсутствует. Исходники сохранены; оставшихся попыток
  нет. Остальные байты JAR и его размер совпали с оригиналом. Дополнительный
  аудит содержит 15 проверок без расхождений.

Нативные сценарии выполнены на локальном kit. Связь с принятыми CI-байтами
проверяется отдельно ниже; ZIP разных окружений не объявляются одинаковыми
заранее. Модель в этих сценариях не вызывалась.

## Контракты и CI

Три RED-кейса cached write/change/size воспроизвели старый отказ. Все 33 новых
контракта прошли после исправления. Отрицательные проверки охватывают
настоящие directory/file mutations, неверные identity/type/attributes/creation/
path, добавление файла, hardlinks, лимит handles, callback error и закрытие
ресурсов. Отдельно проверен `OwnedAttempt.create` → capture inventory → cleanup.

Локальная регрессия runtime/service и DACL: 352 Python-теста. Совместимость,
релизные контракты и live apply/recovery: ещё 77 Python-тестов, включая
38 проверок применения и отката. Companion: 65 Node-контрактов. До добавления
совместимости новый dev13 отвергался прежним адаптером; после изменения
прежние версии поддерживаются, неизвестный `dev999` отклоняется.

В каждом исходном [push CI](https://github.com/DmitrL-dev/1cai-public/actions/runs/36295543652)
и [PR CI](https://github.com/DmitrL-dev/1cai-public/actions/runs/36295545877)
прошли 2439 Python-тестов без failures/errors/skipped, 65 Node-контрактов, Go,
двойная сборка и установленные CLI/MCP, snapshot comparison и observer.
Все 429 локально квалифицированных Python-случаев найдены в каждом JUnit.
В каждом — 24 успешных шага; предварительные 48 ACL/runtime случаев входят
также в итоговые 2439, не прибавляются к ним как уникальные проверки.
Фактический PR checkout — `ab110acb4cef32a1baf00e9038800a9ae4b82438`; его Git tree
`71bfd35fa85e0a0380717877feed8f3f1ccd8f51` совпал с деревом исходного кандидата, родители проверены.
GitHub digest обоих JUnit-артефактов и обоих архивов поставки сверены после скачивания.

## Ограниченная проверка применения BSL на 1С

На установленном локальном wheel `b7b26fcd446e1841bcbc7ef1cb3f4797dd4fc992dfbe212c4555d07bb948b6cd` и 1С 8.3.27.2342
выполнены два proposal precheck: корректный BSL принят, ошибочный дал диагностику.
CLI применил правку к собственной копии синтетического модуля. В новой собственной
файловой базе 1С загрузка, CheckConfig, обновление и исполнение вернули **43**.
После Undo все шесть исходных файлов восстановлены по SHA256, повторное исполнение
вернуло **42**. Сохранены UUID модуля и конфигурации и head проекта; все 11 native
шагов завершились кодом 0 без timeout. Модель не вызывалась.
Полный dump не объявляется побайтно одинаковым из-за служебных данных платформы.
[Квитанция](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/product/evidence/proposal-live-native-dev13-20260927.json)
фиксирует локальный кандидат; равенство его wheel с принятым CI wheel проверено.
Отдельный редакторский сценарий описан в заметках Companion и
[общем протоколе](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/product/NATIVE-DEV13-20260927.md).

## Что остаётся открытым

Контролируемая репродукция доказывает конкретный механизм ложного отказа.
Причина каждого исторического `BSL_INPUT_CHANGED`, `BSL_CLEANUP_FAILED`
и WinError 5 этим выпуском не установлена. Два свежих installer-сценария
не являются статистической гарантией холодного старта. Issue #23 остаётся
открытым до проверки остальных наблюдений; issue #25 о редком timeout CI
также сохраняется.

Полная приёмка Windows SCM, типовых `.cf/.cfe`, расширений, форм/СКД,
рабочей ИБ и внешнего конкурентного изменения исходников не заявляется.
Платформенная проверка выше ограничена собственным синтетическим модулем
и одной закреплённой версией 1С; она не квалифицирует типовые конфигурации. Production deployment требует отдельного ревью и разрешения
владельца. Реализацию, последующую проверку и выпуск выполняет основной
агент без субагентов по указанию владельца; новое независимое peer review
не заявляется.

[Большая цветная схема Рентгена](https://github.com/DmitrL-dev/1cai-public/blob/main/docs/assets/how-rentgen-works.svg)
показывает путь от выгрузки 1С до проверки и решения о правке.
