# Архитектура Рентгена

**Локальное ядро хранит состояние и проверяет операции.** CLI, MCP и редактор
обращаются к нему. Модель предлагает текст; доступ, версия и решение о записи
не определяются её ответом.

[Поддержка платформ](docs/product/PLATFORM-SUPPORT.md) отделяет текущую
Windows-поставку от целевого переносимого устройства. Границы ниже описывают
существующие компоненты, кроме явно запланированного контура диагностики;
выделение адаптеров ещё не означает их приёмку на всех ОС.

## Что находится в репозитории

| Компонент | Ответственность |
| --- | --- |
| `rentgen_core` | Проекты и права, снимки, черновики, квитанции, миграции; CLI и stdio MCP |
| `rentgen_graph` и `go` | Адаптер графа и отдельный Go scanner BSL |
| `rentgen_diagnostics` | Закреплённый runtime BSL Language Server и управление запуском |
| Metadata/proposal adapters в `rentgen_core` | Планы и preview, ограниченные workspace/live writers, undo и recovery |
| `git_observer` / `git_watcher` / service adapters | Находки Git, повторная проверка источника, состояние наблюдения и платформенный lifecycle |
| `integrations/open-editor` | Отдельный профиль редактора и управляемая локальная правка |
| `integrations/vscode-rentgen` | Companion: модули, черновики, сравнение и команды проверок |
| `scripts/verification` | Инструменты квалификации и ограниченные эксперименты; не отдельная готовая IDE |

## Контракты, которые сохраняем

Реестр выбирает проект; состояние проекта хранится отдельно от исходников.
Снимок связывает точные байты и граф. SourceRef указывает на источник внутри
конкретного снимка. Чтение проверяет полномочия и целостность; новый head
не меняет уже выбранную версию.

Правки сохраняются в отдельный черновик. Запись сравнивает ожидаемую ревизию
с текущей. Квитанция позволяет установить результат после потери ответа;
её чтение не повторяет мутацию. Редактор использует публичный CLI,
агент — ограниченный MCP. Права проверяются ядром при выполнении операции.

Диагностика и результат модели не разрешают применение. Сохранённый отчёт
относится к своим входам. `UNKNOWN` или незавершённая операция требуют
разбора/восстановления, а не автоматического повторного применения.

Metadata preview привязан к снимку, UUID и diff. Прямые BSL/Designer XML
writers имеют ограниченный объём, журналы, проверку ожидаемого состояния
и явные undo/recovery. Они не обеспечивают транзакцию всей информационной
базы или защиту от любого постороннего writer между проверкой и заменой.

Git-контур связывает результаты с проверенным committed HEAD и повторно
проверяет входы до публикации. Возможности watcher, scheduler, службы и
уведомлений имеют собственные контракты и области приёмки:
[Git watcher](docs/product/GIT-WATCHER.md), [service host](docs/product/SERVICE-HOST.md),
[доставка](docs/product/NOTIFICATION-DELIVERY.md).

## Направление разделения ядра и ОС

| Граница | Что должно проверяться |
| --- | --- |
| Локальная идентичность | Доверенный process context; совместимость Windows SID; отдельное пространство POSIX principal |
| Доступные операции | Явный статус и причина недоступности до побочных эффектов; доступность не заменяет авторизацию |
| Чтение источников и снимков | Ограниченные bytes, identity/hash, ссылки и подмена путей, время жизни сессии |
| Блокировки и публикация | Координация собственных writers, замена/flush и восстановление; гарантии отдельно по ОС |
| Владение процессами | Ограничение ресурсов, deadline, отмена, завершение принадлежащего дерева и очистка |
| Native-инструменты | Конкретная поставка 1С, EDT, анализатора, редактора или службы |

Первыми выделяются операции локального состояния и чтения истории. Чтение
снимков, захват, процессы и live apply требуют следующих адаптеров и проверок.
Текущие Windows sharing flags нельзя без доказательства заменить обычным
POSIX-дескриптором или advisory lock с тем же обещанием безопасности.

Первый [Rust input core](docs/product/RUST-INPUT-CORE.md) реализован как
экспериментальный Linux sidecar: no-follow acquisition, bounded ZIP import,
хэши и собственная immutable byte session. Он не создаёт published SnapshotRef
и не заменяет Windows retained reader. Python сохраняет authorization/CLI/XML,
Go scanner — прежнюю роль. Следующие части принимаются по контрактам и замерам,
без обещания полной платформонезависимости. [Порядок работ](ROADMAP.md).

## Запланировано: узкое ядро диагностического рассуждения

[План диагностики 1С](docs/product/NARROW-DIAGNOSTICS-PLAN.md) выделяет небольшой
детерминированный Rust kernel над ограниченными версионированными фактами:
гипотезы, выбор различающей проверки, пересмотр по наблюдению, диагноз или
`insufficient_data`. Это будущий компонент, не свойство существующего ZIP reader
или поставляемого BSL Language Server. Первый milestone — обратимый synthetic
loop с held-out оценкой следующей проверки; native probes требуют отдельной приёмки.

Python сохраняет orchestration, доступ и revalidation. Kernel не исполняет
произвольные проверки и не расширяет полномочия. Диагностический envelope
содержит типизированные наблюдения и происхождение, без бизнес-значений, секретов
и строк исходников. Read, check, draft и live write остаются отдельными операциями;
поддержанная гипотеза не даёт права на любую из них. Rust immutable ZIP session
и Go scanner сохраняют действующие контракты.

## Граница доверия

В опубликованном профиле доверены Windows-пользователь и стартовые параметры.
Процессы того же пользователя и доверенные расширения не изолированы друг
от друга. Стандартный профиль не предоставляет агенту применение к живой
конфигурации. Имя/UID другой машины не является разрешением на импортированный
проект; перенос identity/state требует отдельного контракта.

Подробные решения: [публикация](docs/product/SNAPSHOT-PUBLICATION-ADR.md),
[чтение](docs/product/SNAPSHOT-READ-SESSIONS.md),
[состояние операций](docs/product/WORKFLOW-STATE-ADR.md),
[права](docs/product/PROJECT-ACCESS.md),
[локальная правка](docs/product/LOCAL-REPAIR-DESIGN.md).

В текущем пакете нет старого HTTP-портала. Его исторические документы описывают
прежние интерфейсы, а не наличие работающего сервера в поставке.
