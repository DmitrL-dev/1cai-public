# Internal POSIX copied sources and complete generation

These private modules are implementation seams. They do not admit Linux capture,
change public capability reporting, publish a snapshot, or qualify a release.

`capture_posix_sources` owns an actual `_posix_capture_candidate` attempt. While
F2 is active it retains aliases to verified immutable source images and exact
entries, canonical source document, digest, configuration and revision. It returns
an owner only after F2 completes its final inventory, fsync, authorization and
descriptor cleanup successfully. Every F2 attempt remains a staging orphan,
including successful attempts. The copied owner never reads a source pathname.

Use the returned owner in one `with` scope. It rechecks current `analysis:run`,
Principal, project head and the entire source configuration around disclosure.
PID, thread and nonreentrancy guards apply to reads and close. Read byte totals,
entry/source/manifest limits and byte-image memory accounting are explicit.
Closing clears owner references; immutable aliases already disclosed to trusted
code can survive close. This is not revocation of Python objects.

The copied owner's declared operation deadline starts before F2 and is retained
across all later stages, with an explicit maximum of 120 seconds. F2 still has its
own at most 30 second limit. Generation, scanner and graph limits may shorten
their individual stages. The orchestration authorizer must also retain the same
overall operation deadline. No stage resets the original operation clock.

`open_posix_generation` consumes that active exact copied owner and the same
state, Principal and expected head. It creates a fresh exclusive
`generations/<UUID>` under retained private directory descriptors. It copies
verified sources into `sources/<layer>/...`, including XML, binary and empty
files. `scan_directory` is a **borrowed** private directory capability for the
owned scanner. The scanner must not close, mutate or retain it after this owner
exits. No second workspace, live-tree fallback, or `build-work` is admitted.

`seal` consumes the internal byte bundle produced by the concrete graph adapter
and a trusted verified-byte reader factory. These injected in-process objects
are not a security boundary against code executing as the same user. Tests use
the real `RentgenGraphReaderFactory` and owned SQLite image connection, not a
permissive stand-in. The final file set is sources, `graph.sqlite3`,
`inputs/callgraph.ndjson`, `inputs/scanner-coverage.json`, and canonical
`manifest.json`, created **last**. The auxiliary F2 `source-manifest.json` is never
copied into a generation.

Every created file is exclusive, private, single-link, descriptor owned and
fsynced, then re-read with bounded length and exact inode/stamp/size/hash checks.
Exact directory inventory and bottom-up fsync run before sealing and on clean
exit. A private subclass reuses the existing copied generation session for full
manifest/source/derived/graph binding and actual verified SQLite validation,
using the proposed catalog plus current capture authorization in place of a
published catalog lookup. Validation runs at seal and again at clean exit.
There is no long state transaction during copying, scanning or SQLite work.

Source, supplied graph and derived images, simultaneous verification copies,
SQLite image/cache and conservative canonical JSON expansion have a combined
explicit reservation. The verifier's descriptors are charged together with the
writer's retained directory chain. Individual files, paths, total inventory,
total generated bytes, source count and operation lifetime also have bounds.
These are byte-image/descriptor accounting limits, not a hard process RSS cap,
proof of filesystem-wide atomicity, or a claim that the maximum 100,000-file F2
configuration is supported by later stages. Generation/read sessions currently
allow at most 20,000 sources and their independent descriptor limits can be lower.

Only a sealed generation whose final verification, durability, authorization,
cleanup and deadline checks all succeed exposes an immutable
`CompletePosixGeneration`. Its catalog, layers, snapshot and expected head are a
proposal for a later short compare-and-swap. `published` is false. This owner
never inserts a catalog row, changes a head, renames/promotes a tree, deletes an
orphan, repairs foreign permissions, reuses an attempt, or performs garbage
collection. Failure and cancellation preserve the primary error and leave the
unpublished attempt for a separately designed recovery policy.

The local controls use real native POSIX file operations, real F2 and actual
SQLite, with constructed scanner output. Darwin execution does not qualify the
Linux scanner process, GNU/Linux capture, installed integration, native 1C/EDT,
or a full product release. Linux ACL controls run only on actual Linux.
