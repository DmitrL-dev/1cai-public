# Локальная причина отказа BSL Git-аудита

Статус: **реализация в рамках действующего поручения продолжать разработку**.
Отдельное одобрение владельцем именно текста дизайна не заявляется.
План: [проверяемый диагностический срез](../plans/2026-09-27-git-bsl-failure-reason.md).
Дата: 27 сентября 2026 года.
База исследования: публичный `main`,
`ebb4bbbb683b73b473f2b53c10e3310346d44228`, Core `0.1.0.dev11`.
Связанная задача: [issue #23](https://github.com/DmitrL-dev/1cai-public/issues/23).

## Проблема и предел доказательств

`BslLanguageServerAdapter` возвращает `BslAnalysis.reason`, но
`BslGitAnalyzer.__call__` заменяет неполный результат общим
`GIT_ANALYZER_INCOMPLETE`. `GitWatcherScheduler` записывает только этот общий
код в журнал и outbox. После завершения отдельного процесса оператор теряет
внутреннюю причину отказа.

В обычном установленном прогоне №14 зафиксирован общий отказ. Сохранённый
JSON-отчёт разбирается сейчас, но не доказывает, что исходный процесс успешно
прочитал его, получил exit code 0 или прошёл проверку входов. Во внутренних
инструментированных прогонах наблюдался `BSL_CLEANUP_FAILED`; переносить эту
причину на обычный прогон №14 нельзя.

Источники:

- [Код выпущенного Git-адаптера](https://github.com/DmitrL-dev/1cai-public/blob/441e838ca6c02d10a4763ede6152f6517a771304/rentgen_diagnostics/git_bsl_analyzer.py#L188-L201).
- [Проверка сохранённого отчёта](https://github.com/DmitrL-dev/1cai-public/issues/23#issuecomment-5832106338).
- [Место потери внутренней причины](https://github.com/DmitrL-dev/1cai-public/issues/23#issuecomment-5832194108).

## Варианты

1. **Рекомендуется: добавить проверенный код причины в существующий локальный
   журнал.** Получаем причину из обычного процесса GitAuditWorker, используем
   существующую атомарную запись и идентификатор запуска.
2. Отдельно запускать диагностический адаптер с выводом результата. Это полезный
   эксперимент, но он меняет путь вызова и не устанавливает причину отказа
   обычного GitAuditWorker.
3. Сразу изменить повторные попытки очистки. Это может помочь наблюдённым
   инструментированным прогонам, но пока не обосновано для публичного отказа.

## Предлагаемое поведение

При неполном BSL-анализе сервис завершает запуск с прежним внешним отказом.
В `profile/git-journal.json` событие `fatal` дополнительно содержит:

```json
{
  "status": "fatal",
  "code": "GIT_ANALYZER_INCOMPLETE",
  "analysis_failure": {
    "schema": 1,
    "reason": "BSL_CLEANUP_FAILED"
  }
}
```

Это пример формата, а не установленная причина прогона №14.
Поля `run_id`, `cycle` и `updated_at` уже находятся в документе журнала и
связывают запись с запуском. Вложенное поле содержит только версию формата и
один проверенный код. По нему оператор отличает отказ очистки, изменение входа,
отсутствие runtime, тайм-аут или ошибку процесса.

Неизвестная либо непроверенная причина означает отсутствие `analysis_failure`.
Общий отказ остаётся доступен. Отсутствие поля не означает успешной диагностики.
Журнал хранит текущее состояние: следующий запуск заменяет запись. Для
расследования его копируют после отказа до следующего запуска. Этот срез не
создаёт архив истории или неизменяемую квитанцию.

## Передача и проверка данных

1. Небольшой внутренний модуль `rentgen_core/_git_analysis_failure.py` задаёт
   тип ошибки, производный от `CoreError`, и конечный набор допустимых причин.
   Внешние `code`, `message`, `details` остаются совместимыми с текущей ошибкой.
   Причина хранится отдельным внутренним атрибутом, который `to_dict()` не
   сериализует. Модуль не импортирует конкретный Windows-адаптер.
2. `BslGitAnalyzer` после ответа адаптера повторно проверяет авторизацию.
   Отказ авторизации имеет приоритет; причина анализа при этом не передаётся.
   Для обогащения ошибки требуется точный `BslAnalysis` и существующая проверка
   `_analysis_valid(analysis, raw)`: совпадающие байты кандидата, профиль,
   манифест, конфигурация, допустимые типы и согласованный failed/unsupported
   результат. Этот срез не меняет критерии принятия успешного анализа.
3. Допустимы 15 кодов, которые сейчас выдаёт фиксированный адаптер:
   `BSL_CLEANUP_FAILED`, `BSL_COORDINATES_UNSUPPORTED`, `BSL_COVERAGE_MISMATCH`,
   `BSL_ENCODING_UNSUPPORTED`, `BSL_INPUT_CHANGED`, `BSL_OWNER_BUSY`,
   `BSL_OWNER_QUARANTINED`, `BSL_PLATFORM_UNSUPPORTED`, `BSL_PROCESS_FAILED`,
   `BSL_REPORT_INVALID`, `BSL_RESOURCE_LIMIT`, `BSL_RUNTIME_MISMATCH`,
   `BSL_RUNTIME_UNAVAILABLE`, `BSL_SOURCE_TYPE_UNSUPPORTED`, `BSL_TIMEOUT`.
   Допустимо также ровно одно добавление `_CLEANUP_FAILED` к любому из этих
   кодов, соответствующее текущему формированию составной ошибки адаптера.
   Одного совпадения с регулярным выражением недостаточно: произвольная строка
   `BSL_...` может содержать посторонние сведения.
4. `GitWatcherScheduler` принимает дополнительную причину только из этого
   точного внутреннего типа ошибки с общим кодом `GIT_ANALYZER_INCOMPLETE` и
   повторно сверяет её с конечным набором. Обычные `CoreError.details`, текст
   исключения и произвольные атрибуты не копируются.
5. Обогащённое событие передаётся только в `SchedulerJournal.record` на пути
   fatal. Outbox получает прежнее событие из `status` и `code`. CLI сохраняет
   внешний `SERVICE_WORKER_FAILED`; транспортная сериализация `CoreError`
   сохраняет прежний формат. Причина не попадает в уведомления или owner report.

Для существующего `schema: 1` журнала это необязательное вложенное поле в
словаре `event`. Старые журналы читаются прежним способом; новый файл, настройка
пути, дополнительные права и миграция состояния не требуются. Запись использует
существующие ограничения размера, lease профиля, временный файл и замену.
Ошибка записи журнала сохраняет первичный отказ через существующий
`_preserve_primary_error`; диагностика не создаёт повторный запуск анализа.

## Границы среза

Меняются внутренний тип ошибки, передача проверенной причины и локальное
событие журнала. Политика retries, проверка хэшей и retained handles, удаление
scratch, quarantine адаптера и критерии успешного owner report сохраняются.
В журнал не добавляются пути, имена модулей, исходный BSL, stdout/stderr,
тексты исключений, principal или произвольные поля DTO.

Этот срез создаёт доказательство причины будущего отказа. Он сам по себе не
закрывает issue #23, не подтверждает исправление первого запуска и не означает
готовности SCM, типовых конфигураций, живой ИБ или production deployment.

## Проверки реализации

1. Проверенные `BSL_INPUT_CHANGED`, `BSL_CLEANUP_FAILED` и составная причина
   сохраняются в локальном fatal-журнале после выхода отдельного процесса;
   outbox и внешняя ошибка сохраняют прежний контракт. Тест с управляемым
   адаптером помечается как проверка контракта, а не нативная репродукция.
2. Для подменённых candidate hash/size/profile/config, неверного DTO, неизвестной
   причины, строки с путём, управляющими символами или чрезмерной длиной поле
   отсутствует. Ошибка остаётся fatal, findings и успешный owner report не
   появляются. Значения отказа не превращаются в утверждение о проверенном runtime.
3. При отзыве доступа после ответа адаптера причина не раскрывается; сохраняется
   отказ авторизации. Успешные analyzed/unchanged события не получают старую
   причину. Старый журнал без поля читается. Новый запуск очищает прошлое событие.
4. Ошибка записи журнала сохраняет первичное исключение и ограниченную обработку
   вторичной ошибки. Обычный `CoreError` с похожим `details` не обогащает журнал.
   Прямой `CoreError.to_dict()` внутренней ошибки не раскрывает причину.
5. Узкие регрессии: `test_git_bsl_analyzer.py`, `test_git_watcher.py`,
   `test_service_composition.py`. Затем обязательный Product checks на точном
   коммите, независимое ревью и проверка установленного кандидата.
6. Нативная проверка: новый принадлежащий синтетический Git-проект, свежая
   установка закреплённых JDK/JAR, установленный кандидат, отдельный процесс,
   без monkeypatch и диагностических обёрток. Сохраняются хэши артефактов,
   commit, журнал/outbox, exit code и неизменность исходников. При естественном
   отказе сохраняется новая причина; успешный прогон не считается доказательством
   устранения прежней перемежающейся ошибки. В отдельной принадлежащей установке
   перед запуском меняется один байт закреплённого JAR с сохранением размера.
   Контролируемый нативный отказ обязан сохранить
   `event.analysis_failure.reason = BSL_RUNTIME_MISMATCH` в журнале, прежние
   внешние CLI/outbox и отсутствие успешного отчёта. Эта проверка воспроизводимо
   доказывает передачу причины из установленного кандидата даже без естественного
   отказа первого запуска.

## Поставка и checkpoint

Поставка: план реализации, проверяемое изменение, независимое ревью,
CI, кандидат с новой версией и установленная проверка. Принятое изменение
доводится до публичного `main`. `READINESS.md` и issue #23 фиксируют ровно
полученные результаты и сохраняющиеся ограничения. GitHub release получает
подробное описание нового диагностического поведения и проверки артефактов.
Уже опубликованные ZIP/wheel dev11 не заменяются. Production deployment
требует отдельного ревью и разрешения владельца.
