# Непрерывный Git-аудит службы

Дата: 28 сентября 2026 года. Исходная база: `6b775db29f8eb75191981d443a281e28ad181e7c`.
Работа следует общей задаче продуктовой готовности. Выполнение и ревью ведёт основной агент;
отдельное независимое ревью и production deployment этой записью не подтверждаются.

## Наблюдение и цель

ROADMAP, раздел 4, требует непрерывного аудита. Git-службы schema 2/3 сейчас
принимают только `max_cycles` от 1 до 10000; отсутствие поля означает один цикл.
Сам GitWatcherScheduler принимает `None`, но SchedulerJournal ограничивает оба
счётчика значением 10000. Поэтому изменения только парсера недостаточно.

Цель: явный `max_cycles: null` запускает один срок жизни Git-службы до STOP,
SHUTDOWN, сигнала остановки консольного запуска либо ошибки. Отсутствующее поле
по-прежнему означает 1; существующие целые пределы и dry-run сохраняются.

## Рассмотренные варианты

1. Явный null и расширенный формат журнала — выбран. Сохраняет одну аренду
   профиля, один run_id и существующие stop/backoff/recovery правила.
2. Перезапуск после каждой пачки из 10000 циклов — отклонён: меняет смысл run_id,
   счётчика результата и восстановления после аварии, создаёт дополнительные границы.
3. Увеличение одного максимального числа циклов — не обеспечивает явный режим
   работы до остановки и оставляет скрытый предел журнала.

## Контракт конфигурации

`GitServiceConfig.max_cycles` становится `int | None`, default 1. Обе Git-схемы
принимают только None либо целое 1..10000; bool, float, строки, 0 и 10001
отклоняются. Режим `dry-run` не создаёт worker даже с null. Schema 1 не меняется.
GitAuditWorker уже передаёт бюджет в GitWatcherScheduler; внешнего цикла и
автоматического перезапуска не добавляется. STOP завершает текущий tick,
прерывает ожидание и не начинает следующий. Ошибка остаётся ошибкой службы.

## Долговечный журнал

Старый формат schema 1 сохраняется для `cycle` и `failures` в диапазоне 0..10000.
Schema 2 имеет те же поля и scheduler `git-watcher-v1`, но допускает оба счётчика
от 0 до `9007199254740991` (2**53-1, точное представление целого в JSON-клиентах).
Писатель выбирает schema 2, когда хотя бы один счётчик превышает 10000.
Читатель принимает обе версии, проверяя предел для соответствующей версии;
неизвестная версия и bool вместо номера версии отклоняются.

Все пути записи проверяют тип и предел обоих счётчиков до изменения файла,
включая record/stop. Недопустимый счётчик не должен превращать исправный журнал
в нечитаемый. Размер файла остаётся 1 MiB; атомарная запись, fsync, запрет
перезаписи .tmp, идентичность run_id и явный recover сохраняются.

Прерванный schema 2 журнал требует явного recover. Новый запуск начинает
новый run_id с нулевыми счётчиками и обычным schema 1. Старые версии Core
не читают schema 2: откат работающего профиля на старую версию не принимается;
перед откатом необходимы остановка, сохранение свидетельств и отдельная
проверка совместимости профиля. Автоматическая потеря/сброс старого журнала
ради совместимости запрещены.

## Ограничения ресурсов и отказов

В памяти остаются последние 1000 событий; schema 3 не ставит unchanged в outbox.
Лимит outbox 1000 записей и его явное подтверждение владельцем сохраняются.
Полная очередь, нарушение доступа, переписанная история, неподтверждённый runtime
и ошибки целостности останавливают работу согласно прежним правилам.
Непрерывный режим не означает бесконечное дисковое пространство или игнорирование
ошибок. Источники и Git refs не изменяются службой, модель не вызывается.

## Проверка и выпуск

- Контракты null/default/bounded/invalid для schema 2/3, dry-run без worker.
- Остановка в текущем tick и во время ожидания; сохраняются аренда и отчёт.
- Retryable ошибка с остановкой не выдаётся за успешный запуск; fatal сохраняется.
- Реальный файловый журнал на границе 10000/10001, повторное открытие, recover,
  новый run_id; invalid counters/schema не портят прежние байты.
- Сценарий >10000 быстрых fake ticks с реальным журналом, ограниченными событиями
  и без реального sleep. Это проверка scheduler/persistence, не нативного BSL.
- Регрессия service composition, service entry, Git watcher, service host.
- Root review, отдельный исходный CI и последующий CI main.
- После PR38 и выпуска dev15: новая версия Core с собственными сборкой и CI,
  нативная проверка настоящего Git/BSL под LocalService, подробная публикация.

Принятие PR38 schema 1 не принимается за проверку Git-службы schema 3. Типовые
конфигурации, долгий пилот и независимое ревью остаются отдельными требованиями
общей готовности. Текущие опубликованные релизы не заменяются.
