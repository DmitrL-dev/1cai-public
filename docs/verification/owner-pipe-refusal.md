# Проверка отказа через настоящий Windows pipe

## Что уже проверено

На Windows выполнен обмен между проверяющим процессом и одним созданным им клиентом Node:

1. Проверяющий создаёт отдельный Job с лимитом в один процесс и лимитом памяти.
2. Node появляется в этом Job сразу при создании, с приостановленным основным потоком.
3. После проверки процесса проверяющий разрешает ему продолжить работу.
4. Node подключается к локальному именованному pipe и отправляет `BOOTSTRAP`.
5. Проверяющий отвечает `REFUSAL`: для этого клиента запуск обработчика запрещён.
6. Node разбирает ответ, подтверждает отказ и завершает работу с кодом `0`.
7. Проверяющий подтверждает завершение I/O и процесса, пустой Job и закрытие принадлежащих ему handles.

В принятом пробном запуске выполнены четыре операции I/O: подключение, чтение длины сообщения, чтение сообщения и запись ответа. Инициализатор, исполнитель и Core не запускались. Подтверждение роли настоящего Extension Host редактора и выбранная проверка daily/model/task остаются открытыми.

## Почему потребовалось исправление запуска

Первый вариант использовал `CREATE_NO_WINDOW`. Во время подключения в Job оказалось два разных PID. Дополнительное наблюдение через Windows CIM показало `node.exe` и дочерний `conhost.exe`. Проверка остановилась, поскольку ожидала ровно один процесс; очистка завершилась.

Вариант с `DETACHED_PROCESS` прошёл тот же обмен и очистку. Сохранены создание в Job с первого момента, `CREATE_SUSPENDED`, запрет наследования handles и проверка одного точного PID. `DETACHED_PROCESS` допускает последующий вызов `AllocConsole`, поэтому проверка состава Job остаётся обязательной.

## Какие результаты что подтверждают

| Проверка | Подтверждённый результат |
|---|---|
| 17 Python-тестов с Fake backend | Дедлайны, замена политики, отзыв разрешения, удержание незавершённых вызовов и сохранение исходной ошибки |
| 7 Node controls с имитацией окружения | Проверка конфигурации и закреплённых входных файлов до открытия настоящего сокета и компиляции модулей |
| Сборка C11 с `-Wall -Wextra -Werror` | Совпадение проверяемых размеров и смещений структур |
| Вызов `cp_abi` из собранной DLL | Версия и размеры ABI `[1, 8, 80, 2096, 32, 2]` |
| Пробный запуск на Windows | Настоящий отрицательный обмен через pipe, отказ от запуска обработчика и полная очистка |

DLL и временные результаты собираются проверяющим отдельно. В репозитории хранятся исходники и тесты. Этот вспомогательный код расположен в `scripts/verification/`; запуск Core и штатный пользовательский сценарий его автоматически не активируют.

## Локальные проверки исходников

В корне репозитория:

```powershell
python -m pytest -q tests/unit/test_cold_owner_pipe.py
node scripts/verification/test_root_pipe_refusal_config.cjs scripts/verification/root_pipe_refusal_client.cjs
```

Эти команды проверяют сценарии с имитацией backend и окружения. Для проверки на уровне Windows требуется отдельный проверяющий с закреплёнными исходниками, собранной DLL, одноразовым разрешением и ограниченными дедлайнами.

## Устойчивость получения входов CI

Первый CI объединённого `main` после PR #56 остановился на HTTP `502` при получении JDK. До проверки SHA256, распаковки и native stock Git / BSL этот запуск не дошёл.

`Invoke-PinnedRuntimeDownload.ps1` ограничивает получение каждого входа тремя попытками, устанавливает таймаут запроса 120 секунд и паузы 2/5 секунд. Повторы разрешены для HTTP `408`, `429`, `500`, `502`, `503`, `504` и распознанных таймаутов. Неизвестные ошибки и постоянные отказы завершают шаг. Ошибка подготовки повтора сохраняет исходную ошибку запроса.

Точные URL, версии, размеры и SHA256 JDK и BSL JAR проверяются до распаковки. Неверные полученные байты завершают проверку ошибкой. 21 сценарий с имитацией ответов проверяет повторы, исчерпание попыток, постоянные отказы, испорченные файлы и ошибки очистки. Новый шаг CI запускает эти сценарии и 7 Node controls; настоящий native stock Git / BSL остаётся отдельным обязательным заданием.
