# Жизненный цикл одного соединения с владельцем редактора

**Статус: внутренний контракт и проверки на искусственном транспорте.**
Реальный Windows IPC ещё не подключён. Этот срез нужен разработчикам следующего
этапа [подключения владельца редактора](COLD_OWNER_BOOTSTRAP.md).

## Зачем нужен этот компонент

Запрос может успеть заполнить выходные данные, а затем прерваться. Запрос отмены
также может вернуться раньше завершения операции. Если сразу освободить буфер,
незавершённый ввод-вывод может продолжить обращаться к уже освобождённой памяти.

Компонент `scripts/verification/cold_owner_connection.py` сохраняет связанные
ресурсы до наблюдения завершения. Неизвестный результат закрытия оставляет
ресурс удержанным: повторная попытка не должна случайно закрыть другой ресурс.

## Какие записи удерживаются

| Запись | Что связывает |
|---|---|
| `_EditorEntry` | Уже удержанный редактор, его группу, generation и сведения о роли |
| `_EndpointContract` | Один экземпляр соединения, сведения о роли, ABI, правах и передаче ресурсов |
| `_OperationLease` | Политику размеров и сроков, устойчивое хранилище и владельца завершения |

Сессия выдаёт внутренние объекты-маркеры для этих записей. Проверяется идентичность
объектов одной сессии. JSON, PID, nonce, числовой handle или словарь с `accepted:true`
не заменяют запись. Имена с подчёркиванием — соглашение внутреннего API Python;
они не являются границей безопасности. Будущий Root backend должен хранить эти
объекты внутри доверенного процесса.

## Порядок операции

1. Проверить все три записи, их generation, связи, размеры и сроки.
2. Зарегистрировать операцию и удержать выходное хранилище, `OVERLAPPED`, буфер
   и слоты закрытия **до вызова транспорта**.
3. Выполнить запрос вне короткой блокировки владельца. Отдельная блокировка
   сериализует действия с вводом-выводом и используется без ожидания.
4. При отзыве оставить ресурсы удержанными. Отмена означает запрос на отмену.
5. Принять завершение только для того же объекта операции и того же набора ресурсов.
6. Закрывать собственные слоты по одному. Освободить общий буфер после закрытия всех слотов.

| Состояние | Значение |
|---|---|
| `REGISTERED` | Ресурсы уже удержаны; транспорт ещё не вызван |
| `IN_FLIGHT` | Вызов транспорта начат |
| `COMPLETION_PENDING` | Вызов вернулся или прервался; завершение ещё нужно наблюдать |
| `OBSERVED_COMPLETION` | Наблюдено завершение этой операции; идёт освобождение ресурсов |
| `CLOSED` | Все слоты закрыты и общий буфер освобождён |

Перед попыткой закрытия слот получает состояние `closing_unknown`. Исключение
или неизвестный результат сохраняет это состояние и хранилище; повторное закрытие
такого слота запрещено. Явный `False` от проверочного транспорта означает известный
отказ до закрытия и допускает повторную попытку того же слота.

Новый вызов отмены допускается только до `cancel_until_ns`. Новый опрос
завершения и закрытие каждого следующего слота допускаются до `closure_until_ns`.
Истёкший срок отзывает операцию и сохраняет незавершённые ресурсы. Вызов,
начатый в пределах срока, может сообщить свой результат; новый бюджет не выдаётся.
Само истечение срока не означает завершения или освобождения буфера.

Первоначальная ошибка отправки сохраняется и повторно выбрасывается без замены
ошибкой отмены или очистки. Позднее завершение позволяет очистку; отозванная
сессия при этом остаётся отозванной.

## Проверка разработчиком

```powershell
python -m pytest tests/unit/test_cold_owner_connection.py -q
```

Два сценария проверяют отказ до отправки при отсутствующих или поддельных записях
и цепочку «заполнение выхода → прерывание → отмена → позднее завершение →
неизвестное закрытие». Транспорт перехвачен; значения размеров и сроков в тестах
являются искусственными. Второй сценарий также проверяет отказ повторной
отправки после начавшейся очистки или полного закрытия и запрет новых действий
при истечении срока, используя детерминированные часы без ожидания.

## Следующий этап

Публичный вход `dispatch_registered_operation` пока возвращает
`OWNER_TRANSPORT_NOT_ADMITTED`. Проверочный транспорт подключается только через
внутренний вход тестов. Компонент не открывает Windows pipe, не запускает редактор,
Core, SDK или модель и не выдаёт READY, разрешение загрузки модели либо Native.

Для настоящего транспорта нужны удержанная идентичность extension host,
подтверждённые роли, точные Windows ABI и права endpoint, доверенная передача
ресурсов, измеренная политика памяти и сроков и реальный сборщик завершений.
Положительные проверки этого среза не заполняют эти сведения. Ранний отказ
launcher `DAILY_ROOT_EDITOR_OWNER_REQUIRED` остаётся действующим.

## Прикладной кадр Python в проверочном контуре

**Статус: реализован проверочный контракт; шесть узких Python-тестов прошли.**
Код находится в `scripts/verification/cold_owner_connection.py`. Независимое
Source-ревью и исходные полные CI этого кандидата проходят отдельную приёмку.

Python проверяет один полностью собранный `BOOTSTRAP` из
[Node-моста](COLD_OWNER_NODE_BRIDGE.md) и подготовить один `REFUSAL`.
Готовые неизменяемые `bytes` берутся из буфера той же операции. Сборка фрагментов,
socket, Windows pipe, новая очередь и новая операция в этот срез не входят.

### Как связывается запрос

Кадр — это четыре байта длины тела в порядке big-endian, затем плоский JSON
в UTF-8. Размер тела должен совпасть с заголовком и уложиться в исходные лимиты;
хвостовые байты, неполный кадр и повторные JSON-ключи отклоняются.

Схема задана контрактом. До отправки Root сохраняет `run_nonce`, поколение
`connection_generation`, `request_id` и `bindings_sha256`.
Запрос имеет тип `BOOTSTRAP` и номер `sequence: 1`; ответ — `REFUSAL`,
`sequence: 2` и код `DAILY_ROOT_EDITOR_OWNER_REQUIRED`. Ответ использует
сохранённые значения. Совпадение JSON-полей связывает сообщения с запросом,
но не подтверждает личность редактора.

Также требуются ровно та же операция, её token, объект lease и набор ресурсов
`bundle`; прикладное хранилище должно быть именно `bundle.buffer`. Копия объекта, другой буфер,
неотправленная или отозванная операция не подходит. Разрешена одна попытка
прикладного наблюдения: повтор не создаёт второй ответ и не переотправляет запрос.

### Когда можно освобождать байты

`REFUSAL` сообщает об отказе прикладного обмена. Он не является внутренним
`_Completion`, завершением native IO или разрешением очистить буфер.
Отмена, истечение срока и неизвестный результат закрытия также оставляют
байты удержанными до разрешённого завершения той же операции.

При регистрации необязательного прикладного участка сохраняется исходный объект
политики. Его лимиты и абсолютные сроки используются при отправке, проверке
ответа, отмене, опросе завершения и перед закрытием каждого слота. Подмена
`lease.policy` не выдаёт новый срок или бюджет.

Только после принятого завершения той же операции и успешного закрытия всех
собственных слотов очищаются входные байты и ответ. Ссылка прикладного участка
на storage также отсоединяется; очистки одного `bundle.buffer` недостаточно.
Можно сохранить числовую сводку размеров и первую ошибку. Это описание логического
жизненного цикла, а не подтверждение измеренного расхода native памяти.

### Четыре семейства проверок

1. **Связь, одна попытка и освобождение.** Проверить точный ответ и идентичность
   операции/lease/buffer, отказ для копий и неотправленного запроса. Пока завершение
   ожидается, байты остаются; после успешного закрытия удаляются обе записи байтов
   и ссылка на storage. Повтор наблюдения не выдаёт второй ответ.
2. **Формат и лимиты.** Отклонить неверные nonce/id/hash, логическое значение вместо поколения, номер или
   тип сообщения, лишние и повторные ключи, экспоненциальное число, неверный UTF-8,
   нулевую/избыточную длину, усечённый кадр и хвост. Проверить, что запрос вместе
   с ответом помещается в исходный резерв.
3. **Отмена и исходные сроки.** Отмена во время разбора или пересечение срока
   ответа не публикуют ответ. Подмена политики не разрешает новую отправку,
   отмену, опрос или закрытие следующего слота после исходной границы; удержанные
   байты сохраняются.
4. **Завершение и первая ошибка.** Заполнение кадра перед прерыванием отправки
   не заменяет исходную ошибку. Словарь с обещанием успешного завершения
   не заменяет `_Completion`; ошибка отмены и неизвестное закрытие не подменяют
   первую ошибку и не разрешают преждевременное освобождение или повторное закрытие.

В том же файле сохранены прежние два сценария и добавлены четыре новых семейства.
Root выполнил все шесть узких тестов: шесть pass, без ошибок и пропусков. Публичный `dispatch_registered_operation`
продолжает отказывать `OWNER_TRANSPORT_NOT_ADMITTED`; READY и запуск модели
не разрешаются. Реальный транспорт, доверенный владелец и Windows ABI остаются
следующими отдельными этапами.

## Два исправления после независимого ревью

К начальному набору из шести тестов добавлены две проверки найденных дефектов.
На прежнем коде обе воспроизвели ошибки; после исправления прошли все восемь
тестов, без ошибок и пропусков. Это узкий опыт с искусственными байтами,
часами и port; полного CI или нативного запуска этим результатом не заменяется.

* До первой отправки проверяются исходные storage, policy, вместимость и резерв.
  Проверка повторяется после чтения часов. Подмена буфера или политики, изменение
  лимита либо отзыв во время чтения часов дают окончательный отказ без отправки.
  Возврат прежних объектов не разрешает начать отозванную операцию заново.
* Ошибка разбора может удерживать пакет через traceback, context и cause.
  При успешном завершении и закрытии всех собственных слотов эти принадлежащие
  прикладному разбору диагностические ссылки отсоединяются, а сама первая ошибка
  сохраняет идентичность. Ожидающее или неизвестное закрытие сохраняет сведения
  и байты. Первичная ошибка отправки принадлежит прежнему жизненному циклу;
  её объект и прежние диагностические сведения сохраняются.

Проверена очистка собственных ссылок этого контракта. Ссылки внешнего проверочного
кода и реальный расход памяти процесса этим опытом не аттестованы. Публичная
отправка по-прежнему отказывает `OWNER_TRANSPORT_NOT_ADMITTED`.
