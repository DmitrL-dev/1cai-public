# Three-way update planning

`rentgen_core.three_way.plan_three_way()` строит ограниченный dry-run по трём
явно переданным деревьям байтов: `base` — последняя общая версия, `current` —
конфигурация с доработками, `upstream` — новая типовая версия. Функция не
записывает файлы, не запускает 1С/EDT и не делает автоматический merge.

```python
from rentgen_core.three_way import plan_three_way

plan = plan_three_way(base_files, current_files, upstream_files)
```

Для каждого canonical repository-relative path результат выбирает одно из
действий:

- `unchanged` — все три версии совпадают;
- `same_change` — current и upstream внесли один и тот же результат;
- `keep_current` — upstream совпадает с base, поэтому доработка сохраняется;
- `take_upstream` — current совпадает с base, поэтому принимается обновление;
- `conflict` — обе стороны изменили один путь по-разному, включая
  неоднозначные удаления.

План содержит digest каждого входного дерева, размеры и SHA-256 файлов, но не
возвращает содержимое. Проверяются относительные пути, регистр/Unicode
коллизии, типы байтов и лимиты файлов/объёма. Повторный вызов с теми же входами
даёт байт-в-байт одинаковый JSON.

Это безопасная основа для обновлений, а не готовый перенос конфигурации:
семантика объектов и UUID, владельцы слоёв, формы, СКД, расширения, тестовая
база, backup и rollback потребуют отдельного native EDT/1С адаптера и
evidence-пакета. До этого `conflict` должен быть разобран человеком или
следующим квалифицированным этапом; автоматическая запись отсутствует.
