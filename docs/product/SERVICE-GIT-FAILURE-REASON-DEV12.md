# Core dev12: локальная причина отказа Git-аудита

27 сентября 2026 года проверен установленный кандидат Core `0.1.0.dev12`
из коммита `a35711ca3d1363896afcbc0781a1518161874abb`. Обычный service CLI
сохранил проверенную причину отказа BSL только в локальном журнале.
Отдельный успешный запуск создал отчёт с настоящим замечанием BSL-LS.
Первая установка в этой серии завершилась ошибкой до запуска worker.

[Машинная квитанция](evidence/service-git-failure-reason-dev12-20260927.json)
содержит привязку байтов, все три результата и хэши локальных доказательств.
[Публичный протокол](https://github.com/DmitrL-dev/1cai-public/issues/23#issuecomment-5851674397)
сохраняет результат до окончания полной CI-квалификации.

## Новый контракт

После `GIT_ANALYZER_INCOMPLETE` журнал `profile/git-journal.json` может содержать:

```json
{
  "status": "fatal",
  "code": "GIT_ANALYZER_INCOMPLETE",
  "analysis_failure": {"schema": 1, "reason": "BSL_RUNTIME_MISMATCH"}
}
```

Причина записывается только после проверки точного DTO адаптера, его привязки
к анализируемым байтам, разрешённого кода и повторной авторизации. Scheduler
повторно проверяет внутренний тип ошибки и код причины. Неизвестный ответ
оставляет прежний общий отказ. Наружный service CLI сохраняет
`SERVICE_WORKER_FAILED`, а outbox — общий fatal `GIT_ANALYZER_INCOMPLETE`.

Журнал хранит последнее состояние, поэтому его нужно скопировать до
перезапуска. `run_id`, `cycle`, `updated_at` связывают запись с запуском.
Новый архив ошибок или миграция состояния не добавлены. Подробности находятся
в [описании службы](SERVICE-HOST.md#local-bsl-failure-reason-core-dev12-candidate)
и [спецификации](../superpowers/specs/2026-09-27-git-bsl-failure-reason-design.md).

## Что именно запускалось

Для каждого опыта создан отдельный синтетический Git-проект, registry,
snapshot, профиль и runtime. Использованы штатный installer и установленный
`rentgen-service.exe --console` с schema 2, `read-only`, одним циклом.
В runtime и worker не применялись hooks, probe или monkeypatch.

| Опыт | Установка | Служба | Проверенный результат |
|---|---|---|---|
| 1: исправные входы | Отказ `BSL_INPUT_CHANGED` | Не запускалась | Ошибка сравнения directory inventory в `verify(stage)`; staging сохранён |
| 2: своя установка и изменение первого байта её JAR | Успех, 490 файлов JDK | Exit 2 | Точный локальный `BSL_RUNTIME_MISMATCH`, прежние внешний JSON и outbox, owner reports отсутствуют |
| 3: исправные входы в новом отдельном проекте | Успех, 490 файлов JDK | Exit 0, один цикл | `analyzed`, настоящий `bsl/MagicNumber`, quality `available` / `git_source_verified` |

В опыте 2 изменена только собственная установленная копия JAR. Размер
131 962 428 байт сохранён. Отказ проверки хэша происходит до запуска Java;
этот сценарий не проверяет ошибку процесса Java или его последующую очистку.

В опыте 3 owner report связан с project ID, snapshot ID, Git commit и
`owner_report_id` в outbox. Единственное открытое замечание относится к
числу `10` в строке 2 синтетического модуля. Бизнес-метрики недоступны:
runtime-адаптер для них не настроен.

После завершения процессов отдельно сверены полные внешние JSON и
соответствующие пустые stdout/stderr. Дополнительный reason отсутствует вне
журнала; в успешном опыте его нет и в журнале. Источники во всех трёх опытах
побайтно совпали с исходными UTF-8 без BOM / CRLF строками генератора. Git
нормализовал blob в LF; поэтому чистый checkout проверен дополнительно,
а сохранность CRLF установлена прямым сравнением байтов.

  совпали между установленной копией, wheel и точным исходным Git-коммитом.

  контракт использует управляемый watcher; управляемый адаптер проверяется

  репродукцией старой ошибки runtime.

## Что остаётся открытым

Успех опыта 3 не отменяет неуспех опыта 1. Холодная надёжность установки не
принята; [issue #23](https://github.com/DmitrL-dev/1cai-public/issues/23)
остаётся открытым. Причина старого публичного прогона №14 неизвестна.
Контролируемый `BSL_RUNTIME_MISMATCH` нельзя переносить на тот прогон.

Проверены console mode и синтетические BSL-источники на одном Windows-хосте.
Windows SCM, типовые `.cf/.cfe`, живая ИБ, новый VSIX в нативном редакторе и
полная продуктовая готовность этим протоколом не принимаются. Production
deployment требует отдельного ревью и разрешения владельца.
