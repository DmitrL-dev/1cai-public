# Черновики в браузерном редакторе

Реализовано в development checkout, 2026-09-09. Нужны HTTP-сервис с
[API черновиков](PROJECT-DRAFTS-HTTP.md), состояние проекта schema4 и доступ к
сохранённому снимку. Ранее собранные wheel/sdist dev2 этой реализации не содержат.

В разделе «Редактор BSL» выберите модуль, измените текст и название, нажмите
«Сохранить черновик». Сервер хранит текст и историю в SQLite проекта. Исходная
конфигурация при этом не меняется. Сохранение фиксирует текст на момент нажатия:
можно продолжать печатать, последующие правки останутся несохранёнными.
Кодировка UTF-8, BOM и LF/CRLF сохраняются по политике исходного модуля.

Список «Сохранённые черновики» доступен участникам проекта с `project:read`.
Сохранение, архив и возврат из архива требуют также `source:edit`. Запись содержит
проверенного сервером автора. Открытие черновика читает его исходный снимок,
даже если проект уже опубликовал новый. Названия снимка списка модулей и исходного
снимка черновика показаны отдельно. Автоматического переноса правок на новый
снимок нет.

«Взять текст версии» загружает старый текст в редактор. После явного сохранения
он становится новой версией; история остаётся прежней. Архив также создаёт новую
версию, после чего редактирование недоступно до возврата из архива. При изменении
статуса ввод временно отключён. История и списки загружаются страницами.

Перед сменой проекта, модуля, черновика, раздела или выходом редактор предупреждает
о несохранённых правках. Для перезагрузки и закрытия вкладки используется штатное
предупреждение браузера. Принудительный выход или потеря прав очищает защищённое
содержимое. Если другой автор успел сохранить новую версию, локальный текст
остаётся доступен для скачивания; «Открыть актуальную версию» после подтверждения
заново читает серверное состояние.

Если ответ сохранения потерян, новая запись блокируется до проверки результата.
В браузере до отправки записываются только идентификаторы операции, проекта,
черновика, ожидаемая версия, действие и хеш предложения. Журнал разделён по
доверенному realm, автору и проекту; текст, название и токен в него не входят.
После перезагрузки и входа тем же пользователем кнопка «Проверить результат»
читает квитанцию с сервера. Автоматического повторного POST нет. «Убрать ожидание»
удаляет только локальное ожидание: уже выполненную сервером запись это не отменяет.
Если localStorage недоступен или повреждён, отправка новой записи прекращается
до исправления хранения. Очистка данных браузера удаляет локальный журнал.

Если исходный снимок недоступен, сохранённый кандидат можно читать и скачать.
Редактирование и проверки возобновляются после восстановления доступа к исходнику.
Сохранение не означает успешную BSL-проверку, прохождение тестов 1С или применение
правки. Реальная платформа 1С в этой поставке пока не проверена; её установку
пользователь отложил.

## Проверка

Сценарии находятся в `portal/tests/live/drafts-*.browser.js.template`. Подготовка
изолированного окружения: `scripts/verification/project_portal_acceptance.py setup`,
затем `grant-editor --run UUID`, `serve --run UUID` и Vite с
`VITE_API_PROXY_TARGET`, указывающим на созданный локальный HTTP endpoint.
Используются настоящий JWT, SQLite, Windows SID и Go-снимки синтетических проектов;
полный production lifespan приложения этим стендом не проверяется.

`prepare_project_portal_browser.py prepare --run UUID --phase PHASE --origin URL`
создаёт сценарий в приватном каталоге запуска. Вывод Playwright CLI целиком
перенаправляется туда: CLI печатает исполняемый код с тестовыми учётными данными.
Команда `result` экспортирует только проверенный JSON без этих данных.

Порядок: `drafts-save`, закрытие браузерной сессии, `drafts-open`, `drafts-races`;
после `publish-s2 --run UUID` — `drafts-scope`. CLI может вернуть управление при
появлении нативного диалога, пока сценарий продолжает работу. Для `drafts-open`
и `drafts-races` законченный результат дополнительно записывается в
`window.__rentgenDraftAcceptance`. Его нужно отдельно прочитать через Playwright,
проверить `stage` и `passed`, затем передать журнал команде `result`. Наличие диалога
или выполнение части сценария не считаются успешной проверкой.

Проверяются сохранение и повторный вход, история, архив, отмена переходов,
конкурирующая запись с 409, ввод во время сохранения, потеря ответа после реального
commit и восстановление без нового POST. Отдельно проверяются старый снимок при
новом head, реальный доступ только на чтение и скачивание кандидата при
искусственно недоступном исходнике. Подмена используется только для доставки
ответов и недоступности исходника; авторизация и записанные данные настоящие.
