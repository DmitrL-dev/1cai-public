# READY intent: первый проверяемый срез

Этот документ описывает проверочный harness для разработчиков. Обычному пользователю
не нужно включать этот режим. Реальный холодный запуск редактора в этом срезе ещё
не подтверждён.

## Что означает READY intent

Это небольшой JSON с наблюдением: какой исходный модуль выбран, какие версии
Core и Companion ожидаются, к каким байтам профиля, сценария и манифеста относится
проверка. Он помогает связать следующие этапы проверки с точным входом.

Сохранение JSON **не выдаёт разрешение** загрузить модель или запустить Native.
`kernel_authority`, `loading_allowed`, `native_allowed`, `runtime_verified`,
`pipeline_verified`, `task_accepted`, `full_product_ready` и
`production_deployment` всегда равны `false`. Проверенный peer, владелец редактора
и разрешения на загрузку/Native остаются `null`.

## Как разделены маршруты

| Маршрут | Назначение | Состояние |
|---|---|---|
| `attempt` | Существующая попытка ремонта и проверки | Семантика сохранена |
| `recovery` | Чтение сохранённых результатов | Семантика сохранена |
| `ready-intent-only` | Отдельное наблюдение без ремонта и тестового запуска | По умолчанию отказ до чтения входов и запуска редактора |

`daily_ready_only.cjs` выбирает только `readyIntentOnly`. В нём нет перехода к
`attempt`. Чистый построитель `daily_ready_intent.cjs` проверяет форму и размеры
наблюдения; он не обращается к редактору, IPC, процессам, модели или Native.

Реальный launcher и окружение редактора отказывают с
`DAILY_ROOT_EDITOR_OWNER_REQUIRED`: авторитетный Root backend для владения
процессами пока не квалифицирован. JSON с `accepted=true`, PID, nonce, маркер
READY и числовой handle не отменяют этот отказ.

## Какие входы проверяются

- Наблюдение: схема `rentgen-daily-ready-observation/1`, режим
  `ready-intent-only`, строгое `ready=true`, сериализованный UTF-8 JSON до 65 536 байт.
- Выбранный `SourceRef`: проект, модуль, исходный SHA256 и snapshot текущего head.
- Профиль, сценарий и frozen manifest: абсолютный путь, размер и SHA256;
  отдельно ожидаемые значения, без подстановки отсутствующего ожидания из наблюдения.
- Контекст модели: только 8192, 16384 или 32768; версии Core и Companion.
- Истории repair/test должны быть пустыми. Исторический offline draft первой
  ревизии допускается: он не является историей запуска модели или Native.

Отдельный `ready-intent.json` имеет схему `rentgen-daily-ready-intent/1`, размер
до 32 768 байт и создаётся эксклюзивно. Ошибка записи или отмена оставляет
результат отказом. После intent не вызываются `repairSource`, `testDraft`,
модельный адаптер или HTTP.

## Что подтверждают тесты

Fixtures проверяют контракт JSON, отказ при изменении входов, отсутствие перехода
к repair/test и ранний отказ до legacy `Popen`/активации. Редактор, файловый вывод,
API и запуск процессов в этих fixtures перехвачены.

Они не подтверждают настоящий холодный запуск, владение деревом процессов,
авторитетный IPC, работу модели, качество ремонта, Native или готовность релиза.
Следующие этапы требуют отдельно проверенного Root владельца и IPC, затем
одноразового разрешения первой загрузки и отдельного барьера Native.

Первый компонент следующего этапа описан в
[подключении владельца редактора](COLD_OWNER_BOOTSTRAP.md). Он проверяет порядок
активации и сохраняет реальный отказ до появления принятого owner backend.
