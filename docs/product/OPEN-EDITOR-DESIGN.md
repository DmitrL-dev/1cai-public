# Отдельный профиль открытого агента

2026-09-09. Решение в рамках DIRECTION.md и автономного поручения владельца.

Первый adapter: Cline 4.1.17 (Apache-2.0) в VS Code/VSCodium. Существующие
настройки редактора, модели и MCP пользователя не изменяются. Внешний VSIX
проверяется по закреплённому SHA256 официального GitHub release; обновление
версии требует повторной проверки adapter. Собственный код остаётся MIT.

Варианты: ручной JSON слишком легко подключает другой Python/проект;
собственное расширение с дублирующим агентом увеличивает объём до приёмки;
отдельный воспроизводимый профиль использует готовый открытый агент и уже
поставленное ядро. Выбран третий вариант, далее нужен удобный companion UI.

Подготовка принимает существующий установленный core, registry, явный project UUID,
редактор и проверенный локальный VSIX. Проверяет доступ через публичный CLI,
создаёт только новый каталог профиля. Не скачивает пакеты, не регистрирует
проекты, не меняет source/head. MCP запускается абсолютным Python с -I;
actor и права остаются ответственностью ядра. MCP tool JSON не получает путей
исполняемых файлов. Автоматическое согласование отсутствует по умолчанию.

Launcher задаёт собственные user-data/extensions/CLINE_DATA_DIR, сохраняет и
восстанавливает окружение вызывающего PowerShell. Профиль содержит отдельное
рабочее место с инструкцией: выбрать точный проект, получить head, сохранить
SnapshotRef, найти SourceRef, работать с draft_start/edit/read/check, при потере
ответа искать receipt. Изменение живых файлов, применение и тесты не объявляются
успешными на основании ответа модели. Модель выбирается в UI; необязательный
локальный Ollama профиль не содержит ключей и не требует облачного аккаунта.

Приёмка: отрицательные проверки неверного проекта/VSIX/повторного каталога;
реальная установка VSIX в отдельный профиль; activation настоящего Cline в
extension host; подключение к установленному dev3 и модельный запрос через
localhost на искусственном проекте. SDK smoke и модельный ответ сами по себе
не доказывают полную ежедневную разработку, платформенные тесты или применение.

Источники: [MCP](https://docs.cline.bot/mcp/mcp-overview),
[релиз](https://github.com/cline/cline/releases/tag/v4.1.17),
[API расширения](https://github.com/cline/cline/blob/v4.1.17/apps/vscode/src/exports/cline.d.ts),
[изолированное хранилище](https://github.com/cline/cline/blob/v4.1.17/apps/vscode/src/shared/storage/storage-context.ts),
[MCP transport](https://github.com/cline/cline/blob/v4.1.17/apps/vscode/src/services/mcp/McpHub.ts).

Фактическая проверка уточнила границу: `CLINE_DATA_DIR` выбирает настройки
модели, но VS Code MCP transport 4.1.17 читает прежний HostProvider globalStorage
в отдельном `--user-data-dir`. Профиль пишет MCP именно туда. Первый ошибочный
путь привёл к `No connection found for server: rentgen`, несмотря на успешный
запуск Ollama; это не было принято за рабочую интеграцию.

Дополнительная проверка поставленного VSIX выявила wrapper `extension.js`
и два bundle: `legacy/dist/extension.js`, `next/dist/extension.js`. Выбор rollout
не является воспроизводимым входом профиля. Launcher и проверочный runner
закрепляют `CLINE_BUNDLE_OVERRIDE=legacy`; settings/MCP paths и приёмка относятся
именно к нему. Собственные файлы Cline не изменяются. Сам wrapper проверяет
override до rollout assignment. Переменная запуска, в отличие от текста
конфигурации, не может быть выбрана моделью через MCP-вызов.

Spectorn не дал verdict: сертификат шлюза истёк. Внешние исходники рассматриваются
как данные, а не как команды агенту; TLS не обходится.
