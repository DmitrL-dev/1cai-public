# Core dev10: свежий EDT preview → запись исходников → 1С/YAxUnit

24 сентября 2026 года установленный Core `0.1.0.dev10` из
[публичного ZIP](https://github.com/DmitrL-dev/1cai-public/releases/tag/core-v0.1.0-dev10)
создал **новый** preview переименования
`Catalog.Products.Attribute.Article → SKU` через работающий EDT/MCP 2.16.1.
Это продолжение [предыдущей проверки live writer](METADATA-LIVE-NATIVE-DEV10.md),
в которой preview был синтетическим. Здесь исходный EDT runtime реально
импортировал XML, прочитал метаданные, показал preview переименования,
применил его и экспортировал результат. Весь опыт выполнен на собственном
синтетическом проекте и новых файловых базах 1С.

## Проверенная цепочка

1. Verifier сверил SHA256 публичного ZIP
   `11d5f8e850eec13d9a67c9cd1985db212a076e882b8794cb790fb7ac2dbee4e3`,
   92 установленных файла Core с wheel и `bsl-scan.exe`. Проверены
   зарегистрированный собственный профиль, snapshot, исходный inventory и
   точный manifest фикстуры. Отдельная среда прогона подготовлена офлайн
   по `mcp-requirements.lock` и wheels из этого ZIP; сам verifier состав
   этой среды повторно не проверяет.
2. Core запустил EDT/MCP и сохранил новый preview с ID
   `c07067e01d35621061ddb26bb91b4caeab701b5d0ab0c4d5f391d0df143edbaa`.
   Retained run закрыл runtime штатно; девять вызовов MCP записаны с
   запросами, ответами и хэшами файлов. Два ранних запроса деталей вернули
   ошибку доступа к конфигурации, третий прошёл; импорт, preview и применение
   rename, экспорт получили ответы. Verifier проверил пару `confirm:false` /
   `confirm:true`, совпадение `expectedHash` с preview и результат
   `action: executed`, `performedCount: 1`, `errors: 0`.
   Preview не изменил зарегистрированный источник.
3. Read-only preflight вернул `unavailable`, как и требует старый контракт.
   Отдельный live writer применил сохранённый intent под operation ID
   `b9a46305-ca68-4078-a75d-0aeda63ba613`. Изменились только
   `Catalogs/Products.xml` и `Catalogs/Products/Forms/ItemForm/Ext/Form.xml`.
   Полный inventory источника после записи совпал с candidate свежего EDT
   preview.
4. Именно записанный источник был закреплён на время native импорта в
   новую файловую базу 1С 8.3.27.2342. Шаги `create`, `load-live-source`,
   `update`, `check`, `dump` завершились с кодом 0. Обратная выгрузка
   подтвердила UUID справочника, реквизита и формы, строку длиной 32 и
   привязку поля к `Объект.SKU`; проверка конфигурации не нашла ошибок.
5. CAS undo вернул `undone` и восстановил все пять файлов источника.
   Отдельный YAxUnit 25.12 прогон на inventory этого же preview проверил
   три записи: Unicode, пустое значение и строку длиной 32 символа.
   `seed`, `reopen-original`, `normalized`, `renamed`, `restored` прошли
   по одному тесту; чужой UUID дал один ожидаемый failure без ошибок.

SHA256 полного inventory исходного и восстановленного источника:
`e4099571515b28588939bd20df1b29deb39d76dbb16b21b4a8012eaf12de254b`.
После записи:
`8dc3cbb4b4fe91c32543d29125f600565a2ac1052da4173e6b294da7d083cd5c`.
Полные пофайловые хэши, коды 1С, версии и хэши бинарных входов, девять
MCP-вызовов с хэшами журналов, статусы бизнес-тестов и IDs находятся в
[машинной квитанции](evidence/edt-live-native-dev10-20260924.json).
SHA256 квитанции:
`012c477cc9f73f2c51e96d769c6b1c1307fe03a01af070ec291e4e3c7c78348d`.

[Verifier для сохранённого собственного профиля](../../scripts/verification/verify_edt_live_native_dev10.py)
принимает путь к тому же зарегистрированному EDT профилю, публичному
ZIP и `bsl-scan.exe`, `1cv8.exe`, `ibcmd.exe`, YAxUnit CFE, ожидаемые SHA256
и новый `--output` на фиксированном локальном томе. Он сверяет закреплённые
ID проекта, snapshot, профиля и прежнего EDT плана; для другого профиля
нужна отдельная адаптация и проверка. Исполнять его следует установленным
Core dev10 с offline MCP extra из ZIP. Полные локальные
журналы EDT, 1С и YAxUnit остаются в каталоге запуска; абсолютные пути
личного профиля в публичную квитанцию не включены.

## Пределы вывода

EDT действительно создал новый preview, а Core записал выгруженные Designer
XML исходники. Продукт не обновлял рабочую информационную базу; native
проверка и бизнес-тесты использовали новые файловые базы. Доказана одна
операция на собственном синтетическом каталоге. Опыт не квалифицирует
произвольные клиентские конфигурации, `.cf/.cfe`, расширения, формы или СКД
как самостоятельные изменения, внешние конкурентные записи и production
deployment.
