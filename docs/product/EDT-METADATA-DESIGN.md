# Прямое изменение метаданных: проектирование D1/D2

Статус: разработка; структурные записи ещё не приняты. Этот документ сохраняет
обязательный результат стратегии v3: объект, реквизит и поле формы можно изменить
без GUI Конфигуратора, проверить платформой и отменить с сохранением identity.

## Выбранная архитектура

Рентген управляет операцией и доказательствами, отдельный EDT-MCP выполняет
операции модели EDT. Собственный независимый XML writer потребовал бы повторить
семантику ссылок, форм и служебных идентификаторов; прямой вызов произвольного
MCP tool не обеспечивает сохранность исходного состояния. Поэтому первый путь —
типизированный адаптер над EDT с обязательной изолированной копией проекта.
Сторонний Java-код не включается в MIT-ядро. EDT-MCP подключается отдельно на
своих условиях AGPL-3.0-or-later; платформа и EDT остаются внешними зависимостями.

Сначала выполняется настоящий эксперимент с установленным runtime. Схемы
инструментов фиксируются из работающего сервера; README не доказывает их работу.
Изучен upstream `39826d0bfae97e54dbf62a7d598ae45e2dfb8082`. Локально установлен
EDT 2025.1.4, тогда как текущий upstream заявляет 2026.1/2026.2. Для проверки
готовится отдельное окружение 2026.1; существующая установка не обновляется.

## Контракт операции

Вход связывает проект и полномочия локального пользователя, точный SnapshotRef,
упорядоченные слои, ожидаемый UUID объекта, UUID владельца, тип и операцию.
FQN и путь служат адресом для адаптера, но не заменяют identity. Неоднозначные
UUID, неизвестный слой, несовпадение владельца и неподдерживаемый формат дают отказ.
Первая приёмка — базовая конфигурация; расширения требуют отдельной матрицы.

Администратор закрепляет runtime, версию/хэши плагина и перечень возможностей.
Агент не выбирает executable, URL, токен, рабочий каталог, имя чужого проекта
или произвольный инструмент EDT. Секрет локального MCP не входит в аргументы
модели, отчёты и Git. Запросы ограничены loopback и выбранным backend-профилем.

Перед любым внешним действием ядро сохраняет намерение с уникальным operation ID
и исходными хэшами. Один процесс владеет рабочей копией; повторный вызов после
сбоя сначала сверяет состояние. Успех HTTP, MCP и `success=true` не равен
успешному изменению конфигурации. Ошибка, таймаут, неполный экспорт и неизвестный
исход остаются самостоятельными состояниями и не запускают запись повторно.

## Preview, apply, re-read и undo

1. Сохранённые источники материализуются в новую принадлежащую операции копию.
   EDT импортирует её в отдельный workspace. До изменения экспортируются
   исходные метаданные, UUID, ссылки и неизвестные данные для сравнения.
2. Типизированная операция выполняется только в копии. Затем экспортируется
   candidate. Preview содержит фактический diff, добавленные/удалённые identity,
   изменения ссылок, неразобранные файлы и результаты проверок.
3. Apply принимает только уже проверенный candidate. Ещё раз сверяются права,
   baseline и точные хэши preview; изменение живого проекта означает stale.
   Применение к управляемому проекту и публикация результата имеют собственную
   квитанцию. Запись нескольких файлов не объявляется атомарной без доказательства
   протокола восстановления; внешний workspace нельзя считать эксклюзивным по
   наличию одного lock-файла Рентгена.
4. После записи EDT повторно открывает/читает проект, а 1С загружает экспорт
   в новую тестовую базу. Проверяются свойства, UUID, ссылки, форма и исполнение
   проверочного сценария. Исходная рабочая ИБ не участвует в эксперименте.
5. Undo восстанавливает сохранённый baseline только при совпадении текущего
   состояния с результатом операции. Последующая чужая правка вызывает conflict;
   обратный rename или повторный create не заменяет восстановление baseline.

Если import/export теряет неизвестные данные, операция не считается принятой.
Нормализация сериализации описывается отдельно от изменения семантики и не может
скрывать удаление UUID, расширения, элементов формы или нераспознанных свойств.
Эксперимент уже выявил добавление четырёх свойств по умолчанию при import/export.
Поэтому нужны два diff: исходник → импортированный baseline и baseline → правка.
Второй diff не имеет права скрыть первый. Неизвестный эффект преобразования
блокирует apply до явного разрешения в поддержанной матрице и проверки поведения.

## Первый сквозной сценарий и критерии

Собственная тестовая конфигурация содержит справочник товаров. Через EDT
добавляются строковый реквизит «Артикул» и связанное поле управляемой формы,
затем проверяются переименование с сохранением ссылок и отмена. Результат должен
пережить повторное открытие EDT и загрузку в 1С. Тест в платформе записывает
и читает значение реквизита; одной успешной компиляции недостаточно.

Параллельно обязательны отрицательные проверки: устаревший baseline, смена прав,
чужой UUID/слой/проект, неизвестный исход записи, незавершённый экспорт,
перезапуск до квитанции и undo после посторонней правки. Неудачный сценарий
не меняет опубликованный head и не выдаёт частичный результат за готовый.

## План выполнения

- [ ] Поднять закреплённые EDT/EDT-MCP в отдельном Windows runtime, сохранить
  фактические версии и схемы, выполнить import → изменение → export → re-open.
- [ ] Проверить exported candidate реальной 1С, UUID и данным реквизита;
  зафиксировать поддержанный состав объектов/форм и обнаруженные потери.
- [ ] Реализовать профиль backend и типизированный адаптер в `rentgen_core`,
  журнал операций и восстановление; контрактные тесты имитируют отказ транспорта,
  а успешность записи подтверждает отдельный реальный тест.
- [ ] Добавить CLI и команды редактора для preview/apply/result/undo с общей
  проверкой прав и preconditions; выполнить отрицательные сценарии выше.
- [ ] Проверить самостоятельную установку и опубликовать подтверждённую матрицу.

План не закрывает D1/D2 выпуском одного discovery-инструмента. До полной цепочки
preview/apply/re-read/undo и платформенного теста статус остаётся «не принято».
