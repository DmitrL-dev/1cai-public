# Проверка предложения компилятором 1С

Цель: проверить конкретные байты предложения на полной сохранённой конфигурации,
сопоставив результат с проверкой исходного снимка. Это дополнение к BSL LS;
проверка отдельных функций не заменяет контекст компиляции конфигурации.

Реализовано в ветке dev8, команда `proposal-platform-check`:

- Вход: явный проект и снимок, уже существующее BSL-предложение, локальный полный
  клиент 1С и ожидаемый SHA256 его EXE. Требуются `project:read`, `source:edit`,
  `analysis:run`; права проверяются до чтения входов, в ходе процесса и перед выдачей.
- Поддерживается один зарегистрированный слой `base/designer_xml`. EDT,
  расширения и OneScript отклоняются явно. Эти ограничения не означают отказ
  от их поддержки в конечном продукте.
- Материализуются проверенные байты снимка, затем отдельная копия с единственной
  заменой модуля. Живые исходники и рабочая база не используются. XML с DTD
  запрещён. Ограничения: 20 000 файлов, 256 МиБ исходников, 64 МиБ на файл;
  для XML дополнительно 4 МиБ, 50 000 узлов и глубина 64.
- Создаётся собственная файловая база в новом каталоге состояния. Для исходной
  и изменённой конфигурации выполняются загрузка, повторная выгрузка и CheckConfig
  в явно перечисленных контекстах. Модуль должен присутствовать в обратной
  выгрузке и совпасть с ожидаемым текстом после нормализации BOM/переводов строк.
  Так «успех» загрузки без фактического включения модуля не превращается в clean.
- Нет UpdateDBCfg, Enterprise и выполнения пользовательского приложения. Это
  компиляция в отдельной базе, не изоляция процесса от ОС и не бизнес-тест.
- EXE и известные входные файлы удерживаются от записи/удаления на время чтения
  платформой. DLL среды 1С целиком не закреплены; SHA256 EXE не выдаётся за их проверку.
- Код 0 при завершённой проверке означает `passed`, 101 — `diagnostics_present`.
  Остальные коды, таймаут, отсутствие/переполнение журнала и несовпадение обратной
  выгрузки дают ошибку. Исходный и изменённый результаты показаны отдельно;
  из текста журналов не выводится автоматически, какие ошибки внесла правка.
- Ответ содержит SourceRef, content_id предложения, хэши материализаций и
  замены, контексты компилятора, журналы, коды и идентификатор запуска.
  Локальный отчёт — свидетельство без независимой аттестации; применение недоступно.
  Каталог с копиями и журналами остаётся для разбора; прямое чтение тем же SID
  не контролируется API. Удаление старых запусков — отдельная задача.

## Использование

Сначала зарегистрируйте выгрузку и обозначьте её единственный слой как
`designer_xml` командой `layers-set`, затем выполните новый `capture`.
Формат берётся из сохранённого снимка; изменение текущих настроек не меняет
формат старого снимка. В `--layers-json` передаётся файл с массивом:

```json
[{"layer_id":"base","ordinal":0,"kind":"base","root_relative_path":".","source_format":"designer_xml"}]
```

Используйте ожидаемую ревизию из `layers-get`. Получите `proposal.json` обычной
командой `proposal-create`, как в [проверке BSL LS](PROPOSAL-CHECK.md).
Для установленного полного клиента, которому доверяет оператор:

```powershell
$platform = 'C:\Program Files\1cv8\8.3.27.2342\bin\1cv8.exe'
$platformHash = (Get-FileHash -LiteralPath $platform -Algorithm SHA256).Hash.ToLowerInvariant()
rentgen proposal-platform-check --registry C:\RentgenState\registry.sqlite3 `
  --project PROJECT_UUID --snapshot SNAPSHOT_SHA256 --proposal-json .\proposal.json `
  --platform $platform --platform-sha256 $platformHash
```

Сверяйте доверенность установки отдельно: хэш в примере фиксирует выбранный EXE,
а не доказывает происхождение всех файлов установки. Пути EXE и JSON задаёт
локальный оператор; это не параметры удалённого MCP-инструмента.

Успешное завершение команды возвращает JSON и код 0, включая случай найденных
ошибок компиляции: проверяйте `analysis.candidate.status`. Технический отказ даёт
код 2 и объект `error`. `tests.status=not_run` относится к выполнению тестов
бизнес-логики, `apply.status=unavailable` — к применению правки в рабочую базу.
Результат хранится также в `<state-root>/platform-checks/<run_id>/report.json`.
Копии конфигурации и логи могут содержать чувствительные данные проекта.

Лимит каждого из семи процессов — 120 секунд, общий — 600 секунд; журналы
ограничены 128 КиБ каждый. Права перепроверяются примерно каждые 0,5 секунды.
Таймаут, отзыв прав и Ctrl+C завершают только созданное дерево процесса.
Повторный вызов создаёт новый запуск и не продолжает старый автоматически.

## Проверка поставки

На 8.3.27.2342 отдельный установленный wheel прошёл корректное и ошибочное
предложения: исходная конфигурация `passed` в обоих случаях, изменённая —
`passed` и `diagnostics_present`. Хэши предложения/снимка и сохранённого отчёта
совпали, head/SQLite проекта и живые исходники не изменились. Неверный SHA256
EXE отклонён до запуска. Запросов к модели и запуска приложения не было.

Повторяемый сценарий `scripts/verification/verify_proposal_platform_delivery.py`
принимает `--python` отдельной установки, `--scanner`, `--platform`, новый
`--output` и `--fixture` — каталог `first-roundtrip` независимого
[нативного теста](PLATFORM-ACCEPTANCE.md). Обычный CI без 1С проверяет контракты
обработки ошибок и прав; нативные результаты выше получены локально.

Обязательные проверки развития: отозванные права, повреждённый снимок, неподдержанный слой,
неизменность источников/head, отказ подменённому EXE, отмена/таймаут, не включённый
в конфигурацию модуль. Отдельная установка wheel должна пройти настоящий нативный
сценарий с корректным и ошибочным предложением. Прежний независимый
`verify_native_platform.py` остаётся проверкой самой платформенной предпосылки.
