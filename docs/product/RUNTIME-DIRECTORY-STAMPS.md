# Проверка каталогов runtime: воспроизводимый ложный отказ

## Что удалось установить 27 сентября 2026

На этом Windows-хосте воспроизведён `BSL_INPUT_CHANGED` после дополнительного
открытия и закрытия каталога **только для чтения**. Файлы не изменялись.
`RuntimePins.verify` сравнивал два результата enumeration, в которых NTFS
обновила кэшированные `write`/`change` поля одной directory entry.

Один опыт сохранил точную неравную пару перед исходным сравнением. Другой
повторил отказ на неизменённом установленном Core dev12, без подмены класса
или Windows operations. В обоих случаях исходная `tree` проверка прошла,
затем дополнительный read-only open/close вызвал отказ. Все 128 файлов и
полные stamps удерживаемых каталогов сохранились.

Это конкретная воспроизводимая причина отказа. Она не устанавливает причины
всех прежних installer/worker/cleanup failures. [Issue #23](https://github.com/DmitrL-dev/1cai-public/issues/23)
остаётся открытым.

## Почему два чтения могут различаться

NTFS хранит в directory entry копию части метаданных объекта. Эта копия может
обновиться при закрытии дополнительно открытого file object, даже если исходный
handle остаётся открытым. Получение метаданных через handle читает свойства
самого объекта. Microsoft описывает этот механизм в
[статье о репликации метаданных NTFS](https://devblogs.microsoft.com/oldnewthing/20111226-00/?p=8813).
Наши наблюдения связывают механизм с directory times в используемом
[GetFileInformationByHandleEx](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-getfileinformationbyhandleex).
Это локальное доказательство поведения, не обещание одинакового кэша на всех
версиях Windows или файловых системах.

## Исправление в исходной ветке

Для directory entries `_inventory` получает полный stamp через удерживаемый
no-follow handle. Identity, тип, attributes, creation и final path проверяются
при связывании с enumeration; между проверками сравниваются полные свежие
handle stamps. Реальные изменения directory write/change/size продолжают
отклоняться. В первоначальном `self.stamps` не заменяются значения: момент
захвата inventory отделён от момента первого открытия handle.

File entries, хэши, запрет hardlink/reparse, лимит 1080 handles/uncertain handles,
1024 entries и существующее владение при закрытии сохраняются. Каталоги
удерживаются при перечислении, затем повторно используются обходом дерева.
Повторных попыток после обнаруженного изменения не добавлено.

Этого изменения **нет в принятом ZIP dev12**. Первый кандидат `64197b7`
в ветке `codex/runtime-directory-stamps` прошёл локальные проверки, но его CI
выявили отдельное расхождение DACL. История исправления и приёмка источника
`1519d8b` приведены ниже. Итоговый [Core dev13](https://github.com/DmitrL-dev/1cai-public/releases/tag/core-v0.1.0-dev13) опубликован.

сырые локальные receipts, хэши модулей, RED/GREEN и регрессию. Локальные receipts
являются свидетельством исполнителя, не внешней аттестацией.

Повторить автоматические контракты в Windows из исходной ветки:

```powershell
python -m pytest -q tests/unit/test_runtime_pins.py tests/unit/test_git_bsl_analyzer.py tests/unit/test_git_watcher.py tests/unit/test_service_composition.py tests/unit/test_service_entry.py tests/unit/test_service_installer.py
```

Native опыт требует нового собственного дерева: создать 16 подкаталогов по
8 файлов, сохранить ожидаемые размеры/хэши, вызвать штатный `RuntimePins.tree`,
отдельно открыть/закрыть read-only handle каталога и вызвать `verify`. Для
положительной приёмки исправления недостаточно отсутствия ошибки: требуется
зафиксировать хотя бы одно реальное обновление кэшированного timestamp при
неизменных retained stamps и bytes. Если обновления не наблюдалось, такой опыт
не подтверждает данный сценарий.

## Установленный кандидат и отказ первого CI

Локальный комплект из `64197b7caf27d0e67712057d09a81fcac3951306` дважды
воспроизведён и установлен офлайн. Проверены все 103 файла трёх пакетов:
Git archive, wheel и установленное окружение совпадают. Штатный установленный
RuntimePins выдержал пять read-only reopen; пять обновлений кэша действительно
наблюдались, полные retained stamps и исходные байты сохранились.

Отдельный штатный Git/service прогон создал отчёт `bsl/MagicNumber` с
`git_source_verified`, завершился кодом 0 и удалил собственный временный attempt.
На втором свежем runtime изменение одного байта JAR привело к коду 2,
локальной причине `BSL_RUNTIME_MISMATCH` и отсутствию owner reports.
Установленные snapshot и observer verifier также прошли.
[Квитанция локальной проверки](evidence/runtime-directory-stamps-installed-20260927.json).
Эти результаты относятся к указанным локальным байтам и не заменяют CI.

Оба исходных CI `36292625827` / `36292705066` проверили по 2424 случая:
2423 прошли, один завершился отказом сравнения DACL внутри
`OwnedAttempt.create`, до проверки cleanup. Первоначальное описание как ошибки
`CreateDirectoryW` было неточным: последующая диагностика подтвердила успешное
создание каталога и несовпадение строкового представления SID.
[Квитанция неуспешных прогонов](evidence/runtime-directory-stamps-ci-failure-20260927.json).
В тест добавлена регистрация настоящего результата CreateDirectoryW и немедленного
GetLastError, а затем также результата чтения DACL. CI сначала выполняет
контракты RuntimePins и private DACL, затем полный набор;
при успехе полного набора его JUnit заменяет отчёт предварительной проверки.
Сами Win32-вызовы выполняются без подмены результата и без повторных попыток.

В исходниках также исправлены поставляемые команды установки: имена wheel
и каталога сборки теперь соответствуют dev13. README указывает уже опубликованную
пару dev12 / 0.1.12, отдельно обозначая кандидат dev13. Исторические квитанции
dev10/dev11 сохранены. Правки поставляемых инструкций меняют sdist и требуют
новой сборки и CI; прежний локальный комплект не становится новым кандидатом.

## Исправление сравнения прав после диагностики CI

Оба прогона `cc7e7f6` показали один результат: текущий trustee имеет RID 500,
каталог создан успешно, Windows возвращает `D:P(A;OICI;FA;;;SY)(A;OICI;FA;;;LA)`.
Ожидаемая строка содержала полный числовой SID того же локального администратора.
Windows допускает оба вида [SID strings](https://learn.microsoft.com/en-us/windows/win32/secauthz/sid-strings).
Отдельный локальный опыт преобразования подтвердил тот же переход к `LA`;
ACL на диске и учётные записи для этого опыта не менялись.

Теперь и ожидаемый, и прочитанный descriptor преобразуются одной native-функцией
в строку DACL. Строго сравниваются защита от наследования, ACE, права, trustees
и порядок. Ошибка либо пустой результат преобразования останавливают работу
до создания каталога; ошибка LocalFree помечает cleanup_uncertain.
См. [контракт Windows](https://learn.microsoft.com/en-us/windows/win32/api/sddl/nf-sddl-convertsecuritydescriptortostringsecuritydescriptorw).

15 новых тестов дополняют 33 RuntimePins-контракта. Для трёх SID service accounts
прежний код дал ожидаемый RED; тесты с этими идентичностями используют filesystem
seam и настоящие Windows-преобразования descriptor. Это не запуск процесса
под SYSTEM/LocalService/NetworkService. Проверка настоящего OwnedAttempt остаётся
под текущим SID. Восемь отличий политики и ошибки конвертации/освобождения
отклоняются. [Квитанция](evidence/owned-attempt-sddl-20260927.json) связывает
RED/GREEN, регрессию и оба CI-доказательства причины.

Исправление меняет `_owned_attempt.py`, поэтому локальный wheel `64197b7`
и повторная сборка документации `1e96838` не подтверждают новые байты.
Новый установленный пакет и CI требуют отдельной приёмки. Ранний общий
отказ `BSL_PROCESS_FAILED` в иных исторических опытах сам по себе не доказывает
совпадение причины; issue #23 остаётся открытым.
