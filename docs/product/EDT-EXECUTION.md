# Исполнение операций в EDT

Статус: backend в ветке разработки после dev8. План, preview и чтение результата
теперь привязаны к снимку и доступны через [локальный CLI](METADATA-PREVIEW.md).
Автоматические команды редактора и запись в live ИБ ещё не реализованы. Внутренний
`metadata_native_apply` добавляет проверенный native повтор выбранного preview
и apply/undo только в новой принадлежащей Рентгену копии;
[контракт и ограничения](METADATA-APPLY.md#native-edt-и-принадлежащая-копия).

`edt_runtime.edt_session` принимает контекст проекта, административный профиль
среды, UUID операции и проверенный план по сохранённому снимку. Он удерживает общий слот нативного исполнителя проекта,
проверяет и удерживает входы среды, затем резервирует новый каталог
`metadata-runs/<UUID>` через общий `native_resources.reserve_run`.
До создания каталога, request и workspace короткий `native-admission.lock`
проверяет общий предел 256 retained-каталогов компиляции, YAxUnit и EDT,
безопасность существующих каталогов и запас полного запуска: ещё 8 ГиБ
в пределах проектных 32 ГиБ и сверх минимальных 4 ГиБ свободного места.
Политика и лимиты сохраняются в `runtime-admission.json`; точная схема
`runtime-request.json` с полным планом сохраняется. Обе записи предшествуют
запуску Java. Источники
материализуются из retained snapshot, затем удерживаются на время сессии.
Уже существующий каталог
не запускается повторно: требуется сверка состояния вышестоящим workflow.

Отказ admission возвращает `details.admitted=false` и `run_id`, не создавая
UUID-каталог, runtime-request или workspace. После устранения причины такой
непринятый UUID можно передать снова. При ошибке выхода из admission после
создания каталога возвращается `NATIVE_ADMISSION_INCOMPLETE` с `admitted=true`,
`status="incomplete"` и кодом причины. Каталог остаётся, даже если request
ещё отсутствует; повторный вход runtime возвращает `EDT_RECONCILIATION_REQUIRED`.
При `NATIVE_EXECUTOR_BUSY` EDT отказывает до admission, сохраняя порядок
захвата общего слота проекта. Политика `retain_all_no_eviction` сохраняет
также пустые, прерванные и неизвестные попытки. Автоматическое удаление,
освобождение retained-слотов и очистка старых workspace не реализованы;
пользовательские и живые информационные базы не удаляются.

Внутренний `edt_admission` позволяет workflow выполнить эту же резервацию до
собственных артефактов и передать активный одноразовый handle в `edt_session`.
Handle связан с контекстом, profile/operation и точным plan; после использования
или выхода из admission он недействителен. Повторного reserve нет. Обычный
`edt_session` без handle использует тот же путь и сохраняет schema 1 request.
Native apply создаёт intent/preflight/owned tree только после такого admission.

Каждая операция получает свой workspace, случайный Bearer-токен и loopback-порт.
Адрес MCP, токен, имя EDT-проекта `RentgenCandidate`, параметры Java и имена
инструментов не приходят от модели. Дерево процессов принадлежит Windows Job;
закрытие сессии и ошибка завершают его. Runtime удерживается только во время
работы сессии. Это владение процессами, а не изоляция ОС от доверенной среды EDT.

Готовность HTTP ограничена 300 секундами, initialize — 30 секундами, обычный вызов
— 90 секундами; проверяемая при ожиданиях и действиях длительность сессии — 600 секунд.
Права, отключение профиля, состояние процесса и дисковый бюджет проверяются во время
ожидания ответов. Контролируются общие данные platform-checks, test-runs и
metadata-runs. Максимум — 128 вызовов за сессию, сохраняемый JSON — до 2 MiB.
Лимит JSON относится к сохранённому результату, а не к предварительному ограничению
размера сетевого ответа внутри SDK. Очистка workspace и ОС-песочница ещё не реализованы.

`EDTClient` предоставляет внутренние методы импорта из `input`, экспорта baseline
и candidate, ожидания модели справочника и preview/подтверждения переименования
его реквизита. Успешный initialize не считается готовностью модели. Повторяется
только чтение, вернувшее известную ошибку «конфигурация проекта ещё недоступна»;
другие ошибки чтения останавливают последовательность.

До каждого вызова сохраняется `NNN-request.json`; затем отдельно — ответ и исход.
`response_received` означает получение ответа, а не подтверждённую правку.
Отрицательный `isError` не заменяет проверку `structuredContent.success`.
При таймауте, обрыве или невозможности сохранить ответ остаётся `unknown`.
Последующие вызовы этой сессии запрещены. Вызовы записи не повторяются автоматически.
Отсутствующий или повреждённый outcome также требует сверки; наличие request
само по себе не показывает, выполнился ли вызов. Семантическая проверка выгрузки
остаётся обязательной даже после положительного ответа.

Native apply adapter сохраняет собственное намерение до `edt_session`, требует
новый operation ID, сверяет полный baseline до подтверждения rename и полный
candidate после закрытия runtime. Входы, UUID/владелец и оба diff должны точно
совпасть с сохранённым preview; новый contentHash от EDT подтверждается внутри
этой же сессии. Общий deadline native последовательности ограничен 600 секундами.
Любой незавершённый native исход запрещает повтор запуска; файлы рабочей копии
публикуются отдельным CAS writer только после полной проверки экспорта.

## Реальный сценарий 10 сентября 2026

На установленном EDT 2026.1.3 / MCP 2.16.1 исполнитель импортировал собственную
фикстуру `edt-metadata-v1/created`, дождался модели Products, выгрузил baseline,
запросил preview Article → SKU, передал полученный contentHash при подтверждении
и выгрузил candidate. UUID справочника, реквизита и формы, ID поля 7 и ID основного
атрибута 1 сохранились; привязка стала `Объект.SKU`.

Импорт изменил Products.xml и Form.xml; правка затронула те же два файла.
Это два разных сравнения: нормализация импорта не скрыта за переименованием.
Общая семантическая безвредность нормализации пока не доказана.

Полученные пять файлов candidate были удержаны по размерам и SHA256 на время
проверки платформой 8.3.27.2342. Создание новой файловой ИБ, загрузка, обновление,
CheckConfig и обратная выгрузка дали exit code 0. Обратная выгрузка подтвердила
проверяемые UUID, тип реквизита и привязку формы. Бизнес-данные не записывались.
Проверка использовала исходники текущей ветки, а не новый установленный wheel;
AI-модели не вызывались. [Машинная сводка](evidence/edt-executor-v1.json).

В следующем изменении добавлены SnapshotRef, слой и проверка UUID/владельца
перед вызовом, а также два diff с полным перечнем файлов и ограниченным текстом.
Собственная фикстура теперь дополнительно прошла запись/чтение трёх значений
через отдельный профиль 1С/YAxUnit при переходе Article → SKU и возврате схемы;
подробности и отрицательный UUID-сценарий — в [METADATA-MIGRATION.md](METADATA-MIGRATION.md).
До D1/D2 остаются разрешённая матрица нормализации, устойчивые
к прерыванию apply/undo, stale/revoke/conflict и тесты на типовых конфигурациях.

## Native apply в собственной копии, 14 сентября 2026

На прежнем owned-профиле EDT 2026.1.3 / MCP 2.16.1 адаптер
`metadata_native_apply` выполнил новую операцию
`9ab45f2f-c1be-4b57-b5ea-9e9d398f1c0e` по сохранённому preview
`976f3251-43fe-4b7a-bdf8-0a5415fc866c`. До запуска полный source inventory
совпал с `packaging/fixtures/edt-metadata-v1/created`.

Native import → baseline → rename Article/SKU с contentHash → candidate
завершился закрытием runtime. Все три inventory, UUID/owner и оба diff совпали
с выбранным preview. Новый preview ID:
`ca7b57c5e5ff33f4000ee2a4e883c6c2b28a433886363e152be80a600ba6a836`.
Файловая публикация в новый owned root вернула `applied`, явный undo — `undone`.
После undo полные инвентари source и owned tree совпали с исходным состоянием.
Квитанции остались в локальном experiment output; чужие конфигурации и рабочая
ИБ не использовались. Smoke исполнял исходники ветки, не установленный wheel.
[Sanitized evidence JSON](evidence/metadata-native-apply-20260914.json) содержит
пересчитанные полные inventories, хэши квитанций, обе проверки diff и UUID/форму
после undo; локальные абсолютные пути и данные пользователя в него не включены.

Этот smoke проверяет native EDT и файловый apply/undo собственной копии.
Он не запускал 1С и не проверял новые бизнес-данные; связанный запуск 15 сентября
описан в [METADATA-NATIVE-BUSINESS.md](METADATA-NATIVE-BUSINESS.md). Live apply
или семантика нормализации на типовых конфигурациях этим не квалифицируются.
Контрактные тесты отдельно
проверяют stale/revoke/concurrent, неизвестный исход EDT, чужой экспорт,
прерванную файловую публикацию, restore original и конфликт undo.

15 сентября 2026 года отдельный запуск подтвердил запись и CAS undo именно в
зарегистрированном Designer XML дереве принадлежащего профиля; он не открывал
1С и не менял информационную базу. См. [квитанцию live source](evidence/metadata-live-source-20260915.json).
