# Исполнение операций в EDT

Статус: backend в ветке разработки после dev8. План, preview и чтение результата
теперь привязаны к снимку и доступны через [локальный CLI](METADATA-PREVIEW.md).
Команды редактора и применение/отмена ещё не реализованы.

`edt_runtime.edt_session` принимает контекст проекта, административный профиль
среды, UUID операции и проверенный план по сохранённому снимку. Он удерживает общий слот нативного исполнителя проекта,
проверяет и удерживает входы среды, создаёт новый каталог `metadata-runs/<UUID>`
и записывает `runtime-request.json` с полным планом перед запуском Java. Источники
материализуются из retained snapshot, затем удерживаются на время сессии.
Уже существующий каталог
не запускается повторно: требуется сверка состояния вышестоящим workflow.

Каждая операция получает свой workspace, случайный Bearer-токен и loopback-порт.
Адрес MCP, токен, имя EDT-проекта `RentgenCandidate`, параметры Java и имена
инструментов не приходят от модели. Дерево процессов принадлежит Windows Job;
закрытие сессии и ошибка завершают его. Runtime удерживается только во время
работы сессии. Это владение процессами, а не изоляция ОС от доверенной среды EDT.

Готовность HTTP ограничена 300 секундами, initialize — 30 секундами, обычный вызов
— 90 секундами; проверяемая при ожиданиях и действиях длительность сессии — 600 секунд.
Права, отключение профиля, состояние процесса и дисковый бюджет проверяются во время
ожидания ответов. Контролируются общие данные platform-checks, test-runs и
metadata-runs. Максимум — 128 вызовов за сессию, сохраняемый JSON — до 2 MiB.
Лимит JSON относится к сохранённому результату, а не к предварительному ограничению
размера сетевого ответа внутри SDK. Очистка workspace и ОС-песочница ещё не реализованы.

`EDTClient` предоставляет внутренние методы импорта из `input`, экспорта baseline
и candidate, ожидания модели справочника и preview/подтверждения переименования
его реквизита. Успешный initialize не считается готовностью модели. Повторяется
только чтение, вернувшее известную ошибку «конфигурация проекта ещё недоступна»;
другие ошибки чтения останавливают последовательность.

До каждого вызова сохраняется `NNN-request.json`; затем отдельно — ответ и исход.
`response_received` означает получение ответа, а не подтверждённую правку.
Отрицательный `isError` не заменяет проверку `structuredContent.success`.
При таймауте, обрыве или невозможности сохранить ответ остаётся `unknown`.
Последующие вызовы этой сессии запрещены. Вызовы записи не повторяются автоматически.
Отсутствующий или повреждённый outcome также требует сверки; наличие request
само по себе не показывает, выполнился ли вызов. Семантическая проверка выгрузки
остаётся обязательной даже после положительного ответа.

## Реальный сценарий 10 сентября 2026

На установленном EDT 2026.1.3 / MCP 2.16.1 исполнитель импортировал собственную
фикстуру `edt-metadata-v1/created`, дождался модели Products, выгрузил baseline,
запросил preview Article → SKU, передал полученный contentHash при подтверждении
и выгрузил candidate. UUID справочника, реквизита и формы, ID поля 7 и ID основного
атрибута 1 сохранились; привязка стала `Объект.SKU`.

Импорт изменил Products.xml и Form.xml; правка затронула те же два файла.
Это два разных сравнения: нормализация импорта не скрыта за переименованием.
Общая семантическая безвредность нормализации пока не доказана.

Полученные пять файлов candidate были удержаны по размерам и SHA256 на время
проверки платформой 8.3.27.2342. Создание новой файловой ИБ, загрузка, обновление,
CheckConfig и обратная выгрузка дали exit code 0. Обратная выгрузка подтвердила
проверяемые UUID, тип реквизита и привязку формы. Бизнес-данные не записывались.
Проверка использовала исходники текущей ветки, а не новый установленный wheel;
AI-модели не вызывались. [Машинная сводка](evidence/edt-executor-v1.json).

В следующем изменении добавлены SnapshotRef, слой и проверка UUID/владельца
перед вызовом, а также два diff с полным перечнем файлов и ограниченным текстом.
До D1/D2 остаются разрешённая матрица нормализации, устойчивые
к прерыванию apply/undo, stale/revoke/conflict и настоящий тест записи/чтения данных.
