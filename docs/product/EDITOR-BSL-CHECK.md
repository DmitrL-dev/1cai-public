# BSL-проверка сохранённой версии в редакторе

Решение для ежедневной разработки: команда на строке черновика/истории получает
точную сохранённую ревизию, сверяет квитанцию и запускает существующий
`proposal-check` с закреплённым профилем BSL-LS. Это использует уже проверенный
адаптер ядра; отдельный запуск Java из расширения и обращение к модели не нужны.
Проверка текущего несохранённого буфера потребовала бы другой идентичности;
в этом сценарии пользователь сначала сохраняет новую версию черновика.

Запуск ограничен доверенным профилем и одной активной проверкой. Перед вызовом
ядра сохраняются UUID, квитанция и предложение в новой папке `bsl-runs`.
Ответ связывается с SourceRef, content ID, хэшем и размером байтов кандидата.
Файл результата записывается до открытия отчёта. После перезапуска чтение
результата повторно проверяет доступ к сохранённой версии, но не запускает BSL.
Если ответа нет, результат обозначается как неподтверждённый и не повторяется
автоматически. Отмена завершает только собственное дерево процессов.

Результат — локальное неподписанное свидетельство. Ноль замечаний считается
чистой диагностикой только при завершённом анализе, полном покрытии одного
модуля и проверенном runtime. Неполная диагностика, неподдерживаемый модуль и
ошибка запуска не получают статус успешной проверки. Бизнес-тесты — `not_run`,
применение — `unavailable`. Профиль Java/BSL устанавливается отдельно.

План реализации и проверки:

1. Контракт CLI-клиента: проверить принадлежность результата конкретному
   предложению и отказ для ложного clean/другого хэша.
2. Сервис запуска/хранения: ограничения размеров и истории, запись до вызова,
   точная ревизия, отмена, чтение без повторного запуска и проверка прав.
3. Команды редактора и контекстное меню; существующий интерфейс прогресса
   и JSON-отчёта, без добавления отдельного webview.
4. Контрактные тесты и реальный Extension Host: диагностика плохой и исправленной
   версий синтетического модуля, затем чтение отчётов новым процессом редактора.
5. Зафиксировать фактические результаты и обновить CI/версию расширения.

## Проверено на Windows

Companion 0.1.7 разработки в VSCodium 1.135.0 проверил сохранённые версии
синтетического модуля: версия 2 вернула `diagnostics_present` с
`DeprecatedMessage`, исправленная вручную версия 3 — `clean`.
Хэш кандидата версии 3:
`2bf9ab03126c2dceeeafddcda26ee447ea649cb7141cbac85263e50c720498db`.
Профиль BSL-LS подтвердил runtime и полную диагностику одного модуля.
Отдельный новый процесс редактора прочитал те же отчёты без нового анализа.

Проверка использует установленное ядро dev8. Верификатор
`scripts/verification/run_bsl_editor_host.py` принимает явные пути к VSIX,
редактору, тестовому профилю, LOCALAPPDATA с BSL runtime и новому каталогу
результата. `--prior PATH_TO_ACCEPTANCE_JSON` выбирает только чтение прежних
результатов. Профиль должен содержать синтетический сценарий `manual.cjs` с
неизменной версией 3; рабочая пользовательская конфигурация не подходит.

Верификатор сверяет снимок, текущую ревизию, исходный модуль и журнал AI-правки.
Контрактные тесты отдельно проверяют подмену хэша, ложный clean, другую ревизию,
утрату доступа, неизвестный исход, отмену, конкурирующий запуск и прямые argv
без shell. Они не заменяют приёмку на произвольной конфигурации.
