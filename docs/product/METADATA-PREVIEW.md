# План и preview изменения метаданных

Статус: ветка разработки после dev8; ещё не входит в опубликованный release.
Первый поддержанный сценарий — переименование собственного реквизита справочника
в единственном базовом слое Designer XML. Работа выполняется в отдельной копии.
Расширения, другие виды объектов, применение и отмена требуют следующих этапов.

План содержит точный SnapshotRef, layer_id, UUID справочника-владельца и реквизита,
их имена и новое имя. Проверяются реальный XML namespace, принадлежность реквизита,
повторение UUID в метаданных снимка и занятость нового имени без учёта регистра.
Путь каталога служит локатором, а не доказательством identity. Исходники рабочей
папки после capture не читаются. Изменение плана или его digest вызывает отказ.

## CLI

`request.json` для собственной фикстуры содержит следующие поля; SnapshotRef
необходимо взять из опубликованного снимка своего проекта:

```json
{
  "schema": 1,
  "operation": "rename_catalog_attribute",
  "snapshot": {
    "project_id": "UUID проекта",
    "snapshot_id": "SHA256 снимка",
    "manifest_hash": "тот же SHA256 снимка"
  },
  "layer_id": "base",
  "catalog": {"name": "Products", "uuid": "fb28b18e-d2a3-4f48-8390-c0d609c9e7c0"},
  "attribute": {"name": "Article", "uuid": "eb298009-8fc5-4a2f-8812-902daeed99df"},
  "new_name": "SKU"
}
```

```powershell
rentgen metadata-plan --registry C:\Rentgen\registry.sqlite3 --project <project-id> --snapshot <snapshot-id> --request-json C:\Rentgen\request.json
rentgen metadata-preview --registry C:\Rentgen\registry.sqlite3 --project <project-id> --snapshot <snapshot-id> --plan-json C:\Rentgen\plan.json --profile-id <edt-profile-id> --operation-id <operation-uuid>
rentgen metadata-result --registry C:\Rentgen\registry.sqlite3 --project <project-id> --snapshot <snapshot-id> --operation-id <operation-uuid>
```

Сохраните объект `result` первой команды как `plan.json`; внешний JSON-конверт
`{result, request_id}` в аргументе plan-json не принимается. Профиль среды заранее
[регистрирует администратор](EDT-PROFILES.md). Все три команды требуют
`project:read`, `source:edit`, `analysis:run`; проверка прав предшествует чтению
внешнего JSON. UUID операции выбирается до запуска и сохраняется вызывающей стороной.

## Что доказывает результат

`preview_id` связывает результат с проектом, профилем, планом и UUID операции.
Сохраняются три полных списка файлов с размером и SHA256: original, baseline,
candidate. Отдельно возвращаются `normalization` (original → baseline) и `edit`
(baseline → candidate). Удаление неизвестного файла при импорте видно в первом
сравнении и не скрывается за запрошенной правкой. Проверки UUID и владельца
повторяются после импорта до переименования, затем на итоговой выгрузке.

Полнота списка файлов и полнота текстового diff — разные поля. Текст ограничен
256 KiB и 5000 строками на файл, 512 KiB на сравнение; бинарные и не-UTF8 файлы
могут быть представлены только хэшами. Переполнение числа строк вызывает отказ,
пропуск текста по объёму помечается явно. Выгрузка ограничена 8192 файлами,
4 GiB суммарно и 256 MiB на файл; план — одним слоем до 20000 файлов/1 GiB,
с существующими лимитами чтения снимка и XML до 4 MiB. Большой JSON-результат
свыше 2 MiB не публикуется как успешно сохранённый preview.

После закрытия EDT сохраняется `preview.json`. Чтение повторно проверяет план,
исходники, сохранённые выгрузки и вычисляет результат для сравнения с записью.
Изменённый результат или выгрузка вызывают отказ. Повтор metadata-preview с тем
же планом, профилем и UUID возвращает проверенный результат без запуска EDT;
другой запрос с тем же UUID отклоняется. Незавершённая операция не перезапускается:
её исход требует сверки. Возможность автоматического восстановления пока не заявлена.

`platform_check` и `business_data_test` пока равны `not_run`: этот workflow ещё
не подключает платформенные доказательства. `apply.status` остаётся `unavailable`.
Наличие preview не означает разрешения применить изменения к рабочей конфигурации.

## Проверка на настоящей среде

10 сентября 2026 создан собственный снимок из пяти файлов, выполнено переименование
Article → SKU на EDT 2026.1.3 / MCP 2.16.1; чтение и повтор операции дали тот же
preview_id. CLI plan/result/preview проверены через отдельные процессы Python.
Нормализация и правка затронули по два файла. Именно новый candidate дополнительно
проверен вне workflow на 1С 8.3.27.2342: создание ИБ, загрузка, обновление,
CheckConfig и обратная выгрузка — exit code 0. Сохранены UUID и привязка формы.
На этом этапе запись бизнес-данных ещё не проверялась. [Сводка](evidence/metadata-preview-v1.json).
Затем выполнен отдельный [сценарий сохранности трёх записей](METADATA-MIGRATION.md)
на точных выгрузках этого preview. Его `acceptance.json` можно привязать командой
`metadata-evidence`; это не меняет исходный снимок и не разрешает apply.

Следующие этапы: согласованная матрица нормализации, расширение проверки данных,
устойчивые apply/undo с проверкой текущих байтов, смены прав и чужой записи,
затем команды редактора и проверка установленной поставки.
