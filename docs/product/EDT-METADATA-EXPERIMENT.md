# Метаданные через EDT: проверенный эксперимент

10 сентября 2026. Это основание для [адаптера D1/D2](EDT-METADATA-DESIGN.md),
а не готовые команды изменения пользовательской конфигурации.

## Подтверждённая цепочка

В отдельном Windows runtime через настоящий MCP созданы конфигурация,
справочник Products, строковый реквизит Article длиной 32 и форма ItemForm.
Форма получила основную привязку к CatalogObject.Products и поле Article.
После экспорта платформа 8.3.27.2342 загрузила конфигурацию в новую файловую
базу, обновила структуру БД, проверила конфигурацию и выгрузила её обратно.
Сохранились UUID справочника и реквизита, длина строки и DataPath поля.

После перезапуска EDT проект прочитан повторно. Предварительный просмотр
переименования Article → SKU вернул contentHash; вызов применения передал
этот хэш. Экспорт сохранил UUID реквизита и изменил привязку поля на
`Объект.SKU`. Отдельная платформенная проверка этого поколения подтвердила
также UUID формы, ID поля 7 и ID основного реквизита формы 1.

Для проверки отмены остановлен только собственный процесс EDT, проверены
хэши изменённого проекта и сохранённой копии, восстановлены файлы до rename.
Изменённое поколение оставлено отдельно. После нового запуска EDT экспорт
совпал побайтно со всеми пятью XML-файлами до rename. Это проверка восстановления
при эксклюзивном владении тестовым проектом; протокол продуктового undo,
конкурентные изменения и восстановление после сбоя между записями ещё нужны.

## Зафиксированное окружение

| Компонент | Значение |
| --- | --- |
| Eclipse bootstrap | 4.30, Windows x64; SHA512 опубликован в evidence |
| EDT feature | `1.35.3.v202609041212` (канал 2026.1, версия 2026.1.3) |
| Поддержка платформы EDT | `v8.3.27`, feature `0.26.0.v202608270949` |
| Java | Axiom JDK 17.0.16+12, отдельный явно заданный executable |
| EDT-MCP | релиз `v2.16.1`, MCP сообщил `edt-mcp-server` / `2.16.1` |
| MCP protocol / Python SDK | `2025-11-25` / `1.30.0` |
| Платформа | `1cv8.exe` 8.3.27.2342; SHA256 в evidence |

Bootstrap скачан из [официального архива Eclipse](https://archive.eclipse.org/eclipse/downloads/drops4/R-4.30-202312010110/)
и проверен по SHA512. EDT установлен p2 director из официального канала
`https://edt.1c.ru/downloads/releases/ruby/2026.1/` с явными версиями двух features;
дополнительные репозитории — Eclipse 2023-12 и Orbit R20211213173813.
Плагин установлен из локального распакованного ZIP
[релиза EDT-MCP 2.16.1](https://github.com/DitriXNew/EDT-MCP/releases/tag/v2.16.1),
SHA256 `6b98ded657704a2ded4433351dcb1f34ed14f7a2ede20b854911a6301de959a7`.
Метаданные канала изменяемы; одна ссылка на канал не закрепляет сборку.
Существующая системная установка EDT 2025.1.4 и рабочие ИБ не менялись.

Схемы семи операций получены из `tools/list` работающего сервера:
create_project, create_metadata, modify_metadata, rename_metadata_object,
get_metadata_details, import_configuration_from_xml, export_configuration_to_xml.
Наличие схемы само по себе не считается выполнением операции.

## Обнаруженные ограничения интеграции

- Старый мост Рентгена использует заголовок X-EDT-MCP-Token. В выбранном релизе
  с включённым токеном такой запрос получил 401; Authorization: Bearer работает.
  Токен хранится только в настройках собственного тестового workspace.
- `/health` и initialize готовы раньше модели проекта. При раннем чтении
  получен явный отказ. Повторялось только чтение с ограниченным ожиданием;
  операции записи после ошибки не повторялись.
- `get_edt_version` в Eclipse bootstrap вернул версию Eclipse. Версию EDT
  нельзя определять только этим ответом: нужны закреплённые установленные bundles.
- При русской ScriptVariant основной реквизит формы называется «Объект».
  Проверка связывает DataPath с объявленным реквизитом и типом, а не предполагает
  английское имя Object.
- Предварительный просмотр rename показал одну точку изменения, хотя экспорт
  подтвердил также изменение привязки формы. Рентгену нужен полный diff экспорта.
- Импорт сохранённой выгрузки в новый проект и обратный экспорт изменили два
  файла: у реквизита появились MinValue/MaxValue с xsi:nil и пустой строковый
  FillValue; у формы — UseForFoldersAndItems=Items. UUID и проверяемая привязка
  сохранились, но побайтная нейтральность импорта не подтверждена. Эти четыре
  дополнения нужно показывать отдельно от запрошенной правки. Их полная
  семантическая эквивалентность в этом эксперименте не доказана.

## Повторить платформенную проверку

В репозитории сохранены [три поколения XML](../../packaging/fixtures/edt-metadata-v1).
Нужны Windows, Python 3.11 и собственная установленная платформа. Выберите новый
каталог результата; скрипт откажется использовать существующий.

```powershell
py -3.11 scripts/verification/verify_edt_metadata_fixture.py --platform 'C:\Program Files\1cv8\8.3.27.2342\bin\1cv8.exe' --platform-sha256 2a9ef3653367b6de29000a3a51749a19e6450134347925713c9075674e9f0956 --phase renamed --output output/edt-renamed-check
```

Для проверки поколения до rename замените phase на `created` и задайте другой
новый каталог. Для другой установки требуется её проверенный SHA256; успешность
на ней не предполагается заранее. `acceptance.json` появляется после загрузки,
обновления, проверки, обратной выгрузки и сравнения структуры. Журналы и новая
тестовая база остаются в каталоге результата. Python с `-O` запрещён проверяющим
скриптом, чтобы не отключить проверки.

Четыре отрицательные проверки подтверждают отказ при потере UUID реквизита/формы,
изменении DataPath и ID поля. [Сводка доказательств](evidence/edt-metadata-v1.json)
не включает локальные пути, токены и журналы рабочего компьютера.

## Что ещё не принято

Запись/чтение значения реквизита в режиме 1С, открытие формы настоящим клиентом,
полнота неизвестных метаданных, слои расширений, stale/conflict/revoke и штатные
команды Рентгена preview/apply/result/undo. До этих проверок D1/D2 остаётся
незавершённым; результаты этого примера не распространяются на произвольные объекты.
