# Тестирование версии черновика в редакторе

В companion 0.1.8 разработки команды локального CLI вызываются отдельным
клиентом редактора. Новый запуск берёт квитанцию выбранной
строки истории, перечитывает эту ревизию и предлагает только включённые
зарегистрированные профили проекта. Регистрация остаётся административным CLI.

До исполнения редактор сохраняет UUID, квитанцию, предложение и сводку профиля
в собственной истории. Ядро отвечает за запуск и окончательный отчёт. Повторное
открытие результата вызывает только чтение по UUID; неполный запуск не повторяется.
Сверяются проект, SourceRef, content ID, candidate SHA256 и профиль. Для каждого
этапа проверяются точные имена тестов, счётчики и согласованность статуса.
Проваленный тест отличается от технического сбоя и отсутствующего результата.

Изменения: tests-result.cjs — контракт результата; testing.cjs — квитанции и
координация; tests-ui.cjs — команды, выбор и отображение; core.cjs — CLI boundary;
extension.cjs/package.json — подключение. Этапы проверки: отрицательные Node
контракты, реализация, полный набор companion, реальный extension host с
установленным ядром и 1С, второй процесс для чтения отчёта без нового запуска.
Принятые релизы не заменяются.

## Использование

Установите companion 0.1.8 разработки и ядро dev8, содержащее команды
`test-profile-list`, `proposal-test`, `proposal-test-result`. Профиль YAxUnit
заранее [регистрирует администратор проекта](TEST-PROFILES.md). Откройте историю
черновика, выберите строку версии и команду «Выполнить тесты версии», затем профиль.
Несохранённый буфер сначала опубликуйте новой версией черновика. Итоговое сообщение
показывает состояние исходного кода и предложения, JSON содержит список тестов.

Для повторного чтения используйте «Результат тестов» и выберите сохранённый
запуск. Вызов не запускает 1С и работает после отключения профиля при сохранённых
правах доступа. Неполный результат не считается успешным, операция не повторяется.
Регистрация, отключение профилей и пути платформы остаются в административном CLI.

## Подтверждённый сценарий

На Windows с установленным ядром и 1С 8.3.27.2342 реальный extension host
VSCodium выбрал историческую версию 1 при актуальной версии 2. Baseline дал
один failure, candidate выбранной версии — один passed; профиль и proposal content
ID совпали с выбором. Исходники, head и актуальная ревизия сохранились. Во втором
процессе редактора профиль отключён, затем прочитан тот же отчёт. Новых запусков
не появилось, request/report не изменились. Модель не вызывалась.

Результат — [локальное свидетельство](evidence/tests-editor-0.1.8.json).
Финальная VSIX отличается от VSIX запуска только README; это проверено побайтно
по содержимому архива. Восстановление проверено на финальной VSIX. Нет заявления
о типовой конфигурации, бизнес-покрытии или полной изоляции исполняемого BSL.
Новые сборки ядра используют [общий слот проекта, контроль диска и очистку
служебных журналов ibcmd](NATIVE-RESOURCES.md). Сами базы и отчёты сохраняются;
политика длительного хранения остаётся отдельной задачей.

Воспроизведение: `prepare_test_editor_profile.py` принимает Python установленного
ядра, scanner, `bad-source` из платформенной приёмки и JSON регистрации профиля.
Он создаёт новый проект и две разные версии черновика, не изменяя источник.
Затем `run_tests_editor_host.py` принимает этот профиль, VSIX, VSCodium и новый
каталог вывода. Повторный вызов с другим output и `--prior <acceptance.json>`
проверяет восстановление в новом процессе. Обе команды предоставляют `--help`.

## Companion 0.1.10 и установленный core dev10 — 23 сентября 2026

Опубликованный VSIX Companion 0.1.10 (208263 байта, SHA256
`b136bc63c63130d61709724f7e52904eb549120016372caee7df330f93193f25`)
проверен в изолированном extension host VS Code с wheel core `0.1.0.dev10`,
установленным из опубликованного офлайн-комплекта. Для запуска использовались
1С 8.3.27.2342 и закреплённый YAxUnit 25.12 на новых собственных файловых
базах. Подготовительный нативный fail/pass сценарий завершил 15 шагов без
ошибки или таймаута; отдельный установленный CLI подтвердил профиль и отказ
новому запуску после его отключения.

Редактор выбрал **ревизию 1** при актуальной **ревизии 2**. Для baseline один
тест завершился ожидаемым failure; для candidate тот же тест прошёл в другой
файловой базе. Повторное открытие результата в новом процессе редактора после
отключения профиля не создало новых запусков. Исходный модуль, голова проекта
и актуальная ревизия сохранились; модель не вызывалась. Публичная
[ограниченная квитанция](evidence/tests-editor-dev10-20260923.json) фиксирует
хэши VSIX, wheel, платформы, тестовых файлов и локальных исходных отчётов без
публикации путей хоста или SID.

Существующий acceptance harness был запущен из побайтного checkout проверенного
коммита на фиксированном томе; в его временной копии изменён только ожидаемый
номер Companion `0.1.8 → 0.1.10`. Исходный и использованный SHA256 harness
есть в квитанции. Опубликованные VSIX, wheel и исходники продукта не менялись.
Доказательство относится к одному синтетическому BSL-модулю и локальному хосту:
runtime редактора не полностью закреплён и внешне не аттестован. Этот сценарий
проверяет тесты выбранной ревизии, но не live apply в рабочую ИБ, типовые
конфигурации или production deployment.

## Опубликованные Companion 0.1.11 и core dev11 — 24 сентября 2026

Отдельно проверена **опубликованная пара**: публично скачанный
[Companion 0.1.11](https://github.com/DmitrL-dev/1cai-public/releases/tag/companion-v0.1.11)
(VSIX 208753 байта, SHA256
`916e1311a5bd8ea43c05e7220c547239bb056a963b85ab7746a13ff8e67f83d5`)
и установленный из принятого ZIP [core dev11](https://github.com/DmitrL-dev/1cai-public/releases/tag/core-v0.1.0-dev11).
Проверка прошла в изолированном extension host VS Code на одном синтетическом
BSL-модуле и собственных файловых базах 1С 8.3.27.2342 с YAxUnit 25.12.

Редактор выбрал сохранённую **ревизию 1**, хотя текущей была **ревизия 2**.
Baseline дал один ожидаемый failure; candidate прошёл один тест в отдельной базе.
После отключения профиля новый процесс редактора прочитал тот же завершённый
отчёт по UUID, не создав нового запуска. Независимый вызов установленного
CLI подтвердил, что новый запуск с отключённым профилем отклоняется, а повторное
чтение отчёта не меняет его. Исходный модуль и head проекта сохранились;
модель не вызывалась. Хэши релизных файлов, установленного wheel, платформы,
профиля, test request/report и локальных исходных acceptance-файлов записаны в
[ограниченной машинной квитанции](evidence/tests-editor-dev11-20260924.json).

Для запуска использован существующий harness: в его временной копии изменена
только ожидаемая версия Companion `0.1.8 → 0.1.11`; исходный и использованный
SHA256 приведены в квитанции. Предыдущая нативная fail/pass фикстура с 15
шагами служила входом для подготовки нового проекта, а не новым 15-шаговым
запуском dev11. Продуктовые VSIX, ZIP и wheel не изменялись. Проверены один
локальный хост и один синтетический сценарий; полный runtime VS Code не
закреплён и внешне не аттестован. Типовые конфигурации, рабочая ИБ, live apply
из редактора и production deployment требуют отдельных проверок.

Дополнительный запуск на новом проекте подтвердил, что [состав, размеры и SHA256
всех файлов локальной установки VS Code совпали](EDITOR-RUNTIME-PIN-DEV11.md)
в снимках до первого и после второго процесса редактора. Контрольные суммы
дерева установки зафиксированы на границах опыта; системные библиотеки,
user-data и внешняя аттестация в этот манифест не входят.
