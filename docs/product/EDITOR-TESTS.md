# Тестирование версии черновика в редакторе

В companion 0.1.8 разработки команды локального CLI вызываются отдельным
клиентом редактора. Новый запуск берёт квитанцию выбранной
строки истории, перечитывает эту ревизию и предлагает только включённые
зарегистрированные профили проекта. Регистрация остаётся административным CLI.

До исполнения редактор сохраняет UUID, квитанцию, предложение и сводку профиля
в собственной истории. Ядро отвечает за запуск и окончательный отчёт. Повторное
открытие результата вызывает только чтение по UUID; неполный запуск не повторяется.
Сверяются проект, SourceRef, content ID, candidate SHA256 и профиль. Для каждого
этапа проверяются точные имена тестов, счётчики и согласованность статуса.
Проваленный тест отличается от технического сбоя и отсутствующего результата.

Изменения: tests-result.cjs — контракт результата; testing.cjs — квитанции и
координация; tests-ui.cjs — команды, выбор и отображение; core.cjs — CLI boundary;
extension.cjs/package.json — подключение. Этапы проверки: отрицательные Node
контракты, реализация, полный набор companion, реальный extension host с
установленным ядром и 1С, второй процесс для чтения отчёта без нового запуска.
Принятые релизы не заменяются.

## Использование

Установите companion 0.1.8 разработки и ядро dev8, содержащее команды
`test-profile-list`, `proposal-test`, `proposal-test-result`. Профиль YAxUnit
заранее [регистрирует администратор проекта](TEST-PROFILES.md). Откройте историю
черновика, выберите строку версии и команду «Выполнить тесты версии», затем профиль.
Несохранённый буфер сначала опубликуйте новой версией черновика. Итоговое сообщение
показывает состояние исходного кода и предложения, JSON содержит список тестов.

Для повторного чтения используйте «Результат тестов» и выберите сохранённый
запуск. Вызов не запускает 1С и работает после отключения профиля при сохранённых
правах доступа. Неполный результат не считается успешным, операция не повторяется.
Регистрация, отключение профилей и пути платформы остаются в административном CLI.

## Подтверждённый сценарий

На Windows с установленным ядром и 1С 8.3.27.2342 реальный extension host
VSCodium выбрал историческую версию 1 при актуальной версии 2. Baseline дал
один failure, candidate выбранной версии — один passed; профиль и proposal content
ID совпали с выбором. Исходники, head и актуальная ревизия сохранились. Во втором
процессе редактора профиль отключён, затем прочитан тот же отчёт. Новых запусков
не появилось, request/report не изменились. Модель не вызывалась.

Результат — [локальное свидетельство](evidence/tests-editor-0.1.8.json).
Финальная VSIX отличается от VSIX запуска только README; это проверено побайтно
по содержимому архива. Восстановление проверено на финальной VSIX. Нет заявления
о типовой конфигурации, бизнес-покрытии или полной изоляции исполняемого BSL.
Очистка баз, дисковая квота и общий предел одновременных нативных запусков
остаются необходимыми до постоянного автоматического тестирования.

Воспроизведение: `prepare_test_editor_profile.py` принимает Python установленного
ядра, scanner, `bad-source` из платформенной приёмки и JSON регистрации профиля.
Он создаёт новый проект и две разные версии черновика, не изменяя источник.
Затем `run_tests_editor_host.py` принимает этот профиль, VSIX, VSCodium и новый
каталог вывода. Повторный вызов с другим output и `--prior <acceptance.json>`
проверяет восстановление в новом процессе. Обе команды предоставляют `--help`.
