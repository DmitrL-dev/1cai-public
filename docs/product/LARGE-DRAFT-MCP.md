# Работа агента с большим модулем

Рабочая версия от 2026-09-09 поддерживает кандидаты до 1 MiB через сохранённые
версии черновика. Полный текст остаётся в SQLite проекта. MCP передаёт точные
замены, ссылки на ревизии и порции байтов. Новая схема состояния не нужна;
история и квитанции используют существующий контракт schema4.

Дополнены [команды черновиков](DRAFT-MCP.md). Все требуют `project_id`:

| Команда | Другие обязательные поля | Необязательные поля |
|---|---|---|
| `rentgen_draft_start` | `snapshot_id`, `source_ref`, `draft_id`, `title`, `operation_id` | Нет |
| `rentgen_draft_edit` | `snapshot_id`, `draft_id`, `expected_revision` ≥ 1, `operation_id`, `edits` | Нет |
| `rentgen_draft_read` | `draft_id`, `revision` ≥ 1 | `offset` (0), `limit` 1–65536 (8192), в байтах; `encoding` (`base64` или `utf-8`, с dev5) |
| `rentgen_draft_check` | `snapshot_id`, `draft_id`, `revision` ≥ 1, `diagnostics_profile` | Нет |

Start создаёт revision1 с точными байтами сохранённого исходника; SourceRef можно
получить из `rentgen_source_list`. Возвращается квитанция в `result.draft`.
Выбранный snapshot должен совпадать с SourceRef. UUID операции сохраняется до
отправки запроса. После прерывания используется прежний `rentgen_draft_receipt`.

Read возвращает `receipt`, `source_ref`, `candidate_size_bytes`,
`candidate_sha256`, `offset`, `size_bytes`, `base64`, `chunk_sha256`, `next_offset`.
Клиент декодирует base64 каждой порции в байты, проверяет её хеш и добавляет байты
к результату. Для следующего запроса сохраняет ту же revision и берёт next_offset.
Null означает конец. После сборки проверяются полный размер и SHA-256. UTF-8
декодируется после соединения байтов: граница порции может проходить внутри символа.
История читается без открытия файлов снимка.

В dev5 агент выбирает `encoding="utf-8"`: вместо base64 возвращаются `text`
и `encoding="utf-8"`. BOM, CRLF и Unicode сохраняются; SHA256 считается по
байтам `text.encode("utf-8")`. Конец порции отступает до границы символа,
поэтому используйте возвращённый `next_offset`, а не запрошенный limit.
Offset внутри символа и limit, не вмещающий следующий символ, отклоняются
как `DRAFT_READ_INVALID`. Offset в конце возвращает пустую порцию/next_offset=null.
Схема4, права и повторная проверка доступа перед MCP-выводом остаются прежними.
Предел 64 KiB относится к байтам; текст не дублируется полем base64. Старый
режим без encoding сохраняет прежний ответ и произвольные границы байтов.

Edit принимает 1–16 замен. Пример элемента `edits`:

```json
{"old_text":"Возврат СтараяСумма;","new_text":"Возврат НоваяСумма;"}
```

Каждый old_text должен точно и единственным образом встречаться в выбранной
expected_revision. При нескольких совпадениях нужно добавить контекст.
Все совпадения ищутся в исходной версии, замены выполняются одновременно и не
могут перекрываться. Каждая строка ограничена 8192 байтами UTF-8, весь запрос —
24 KiB. Пустой old_text разрешён только для единственной вставки в пустой кандидат.
BOM сохраняется отдельно; текст поиска его не включает. Переводы строк и Unicode
не нормализуются. Нарушение политики байтов, неоднозначность или перекрытие не
создают новую версию.

Успешный edit сохраняет полное новое предложение и возвращает квитанцию. Новый
head проекта не переносит черновик на другой снимок. При DRAFT_CONFLICT нужно
прочитать актуальный черновик и согласовать изменение; автоматического повторения
с новой ревизией нет. Повтор исходной операции восстанавливает результат из той
же неизменяемой базовой версии. Массивы замен с одинаковым каноническим результатом
считаются эквивалентными ядром. Большую переработку можно собирать последовательностью
сохранённых версий; единая multipart-загрузка всего нового файла не реализована.

Check проверяет полный кандидат выбранной revision установленным доверенным
BSL-профилем. Возвращает `result.draft` с `receipt`, `diagnostic`,
`tests={status:not_run}`, `apply={status:unavailable}`. Диагностика содержит
proposal_content_id, связанный с квитанцией. Даже при появлении новой версии
проверяется явно выбранная старая. В запросе нельзя задавать executable или runtime.

Read требует project:read, start/edit ещё source:edit, check — также analysis:run.
Start/edit помечены как изменяющие состояние. Все ответы ограничены 2 MiB с учётом
двух представлений SDK; непосредственно перед stdout проверяются текущие права,
включая analysis:run для вложенной диагностики. Legacy inline proposal/save
по-прежнему ограничен кандидатом8 KiB; при большом файле используется этот процесс.

Приёмка: 77 адресных проверок. Настоящий SDK обработал модуль910049 байт с BOM/CRLF,
сменой снимка и перезапуском сервера; клиент собрал изменённый текст порциями и
сверил хеш. Большой полный get корректно отказал по размеру, чтение порциями прошло.
Один реальный BSL-запуск через обработчик MCP проверил сохранённый кандидат104043
байт. Отдельные SDK-тесты с синтетическим анализатором проверили выбранную старую
ревизию и отзыв analysis:run после сериализации. Предыдущая защита вывода и
восстановление после отмены также прошли регрессию. Платформа 1С не запускалась.

Эти команды включены в состав dev3. Доверенные тестовые прогоны, применение/откат,
структурное редактирование конфигурации, обновления и observer остаются
обязательными незавершёнными этапами общей продуктовой готовности.
