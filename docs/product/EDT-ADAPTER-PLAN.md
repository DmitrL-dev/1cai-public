# Реализация адаптера EDT

Основание: EDT-METADATA-DESIGN.md и выполненный EDT-METADATA-EXPERIMENT.md.
Разработка продолжается автономно по поручению пользователя, без субагентов.

1. `edt_profiles.py`: административный профиль с адресом SHA256, полным
   перечнем файлов plugins и загрузочной конфигурации, Java и ожидаемыми версиями.
   Отключение запрещает новый запуск. Реестр не принимает URL/токен от модели.
   CLI: edt-profile-register/list/disable. Проверки: отказ неадминистратору до IO,
   подмена файлов, некорректный профиль, запрет после отключения.
2. `edt_execution.py`: отдельный workspace, одноразовый секрет, принадлежащее
   операции дерево процессов, проверка версии MCP и ограниченное ожидание модели.
   Профиль и права перепроверяются во время исполнения; зарегистрированные файлы
   удерживаются дескрипторами без разрешения записи. Это не заменяет изоляцию ОС
   и не запрещает создание новых файлов. Никаких произвольных tools/call из запроса.
3. `metadata_plans.py` и `metadata_runs.py`: типизированная операция с настоящими
   UUID и владельцем, exact SnapshotRef, намерение до внешнего действия,
   сохранённый результат без автоматического повтора записи. Materialization
   читает retained источники, а не рабочую папку. Diff преобразования при импорте
   отделён от diff правки; неизвестная семантика не разрешает apply.
4. CLI preview/result и проверка установленного пакета на настоящем EDT.
   Затем реализация apply/undo с проверкой stale, прав, чужой записи и восстановления.
   Проверка записи и чтения данных через профиль 1С обязательна до принятия D1/D2.

Первый шаг является зависимостью адаптера, а не самостоятельным завершением
прямого редактирования. Имена файлов — границы ответственности; общие механизмы
владения процессами и удержания входов переиспользуются из ядра.
