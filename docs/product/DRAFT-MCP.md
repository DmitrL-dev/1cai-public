# Общие черновики через MCP

В рабочей версии от 2026-09-09 локальный MCP содержит одиннадцать команд черновиков
поверх [общей истории schema4](DRAFT-HISTORY.md). Они работают с теми же
черновиками, что CLI и [редактор](DRAFT-EDITOR.md). Ранее собранные артефакты
0.1.0.dev2 этих команд не содержат; состав dev3 включает все одиннадцать.

Запуск и проверка Windows SID описаны в [CORE-MCP.md](CORE-MCP.md). Все команды
требуют `project_id`; пользователь определяется токеном процесса сервера.
Поля actor, principal, permissions, пути runtime и служебная метаинформация
не принимаются. Для чтения нужно `project:read`, для save/archive/restore — ещё
`source:edit`. Start/edit требуют тех же прав, check — ещё analysis:run.
Изменяющие команды помечены `readOnlyHint=false`.

| Команда | Остальные обязательные поля | Необязательные поля |
|---|---|---|
| `rentgen_draft_save` | `snapshot_id`, `proposal`, `draft_id`, `operation_id`, `expected_revision`, `title` | Нет |
| `rentgen_draft_get` | `draft_id` | `revision` ≥ 1; без него последняя версия |
| `rentgen_draft_list` | Нет | `status=active\|archived` (active), `limit` 1–25 (20), `after_draft_id` |
| `rentgen_draft_history` | `draft_id` | `limit` 1–25 (20), `before_revision` ≥ 1 |
| `rentgen_draft_archive` | `draft_id`, `operation_id`, `expected_revision` | Нет |
| `rentgen_draft_restore` | `draft_id`, `operation_id`, `expected_revision` | Нет |
| `rentgen_draft_receipt` | `operation_id` | Нет |

Ещё четыре команды — start/edit/read/check — работают с
[полными большими модулями через сохранённые ревизии](LARGE-DRAFT-MCP.md).

Успех возвращается одновременно в JSON-тексте MCP и `structuredContent`:
`{"result":{"draft":VALUE},"request_id":"..."}`. Для save/archive/restore
VALUE — квитанция ядра; для get — `{receipt, proposal}`; для list —
`{items, next_after}`; для history — `{items, next_before}`. Receipt возвращает
квитанцию либо null. Ошибка использует общий `{error: ...}` и `isError=true`.

Агент сначала выбирает точный снимок и SourceRef, затем создаёт proposal.
Перед первым save он сохраняет UUID черновика, UUID операции и полные параметры
запроса; `expected_revision=0`. Для последующих изменений передаёт текущую
ревизию и новый UUID операции. `DRAFT_CONFLICT` требует прочитать актуальную
версию и согласовать изменение, а не повторять запись с новой ревизией вслепую.
Изменение параметров с прежним UUID операции даёт `OPERATION_CONFLICT`.

После отмены, разрыва соединения или неопределённого исхода агент запрашивает
`rentgen_draft_receipt` с исходным UUID операции. Полученная квитанция подтверждает
запись. Null означает отсутствие квитанции на момент чтения: другой процесс ещё
может заканчивать операцию. Отмена не является откатом. Сервер не повторяет
мутацию автоматически; повтор с абсолютно теми же параметрами идемпотентен.

Новый head проекта не переносит черновик на другой снимок. Save повторно
проверяет сохранённый исходник, включая хеш и политику байтов. Get, list, history,
receipt, archive и restore используют только состояние проекта: даже при
недоступном снимке история остаётся читаемой. Restore возвращает статус active;
для возврата старого текста нужно get с revision и новый save с текущей ревизией.

Границы транспорта: входной кадр 64 KiB, параметры proposal 24 KiB, кандидат
inline 8 KiB, путь 1024 байта UTF-8, заголовок 240 символов/960 байт UTF-8.
Полный ответ черновика ограничен 2 MiB уже после сериализации SDK, включая
текстовую и структурированную копии. Большой сохранённый proposal отклоняется
с `OUTPUT_LIMIT_EXCEEDED`, без усечения. Метаданные и история доступны отдельно.
У предложений/диагностики прежний предел ответа 128 KiB.

Перед записью в stdout повторно проверяются актуальные права. Обе копии ответа
проверяются на защищённое содержимое; потеря или повреждение внутреннего scope
даёт отказ. Scope не передаётся клиенту. Поддерживаемая граница — штатный stdio
server; иной transport вокруг `create_server` должен обеспечить свою проверку.

Приёмка исходных семи команд: 50 адресных проверок, включая настоящий SDK, два серверных процесса,
Windows SID, SQLite, захват Go, S1 после S2, конфликты и историю, отмену до commit,
отключение клиента, убийство процесса после commit, отзыв доступа после
сериализации и ограничения ответа. Диагностика в регрессионных тестах границы
ответа синтетическая; Java и платформа 1С здесь не запускались.

Это готовность хранения черновиков через MCP. Полный ежедневный агентный процесс,
доверенные тестовые прогоны,
применение/откат и выпуск остаются отдельными незавершёнными этапами.
