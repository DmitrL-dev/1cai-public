## Синхронизация с кандидатом 14 сентября 2026

Числа тестов и статусы ниже относятся к указанным историческим SHA. Для
актуального кандидата используйте [READINESS.md](READINESS.md). Для SHA
`1a1015b12b7d2271a56ec821c1037dd56a128064` собрано 1936 тестов: 1933 прошли,
3 ожидаемо пропущены из-за ограничения Windows на создание симлинков.
Это результаты указанного SHA, а не последующих изменений. После этого аудита добавлены bounded native
admission/retention, прямой Python ImagePath для SCM-плана, отдельный plan-only
`ibcmd` create/import/export с локальным fixture evidence, schema 2 composition
root для bounded Git/BSL/owner-report цикла, offline retained-register producer
native EDT adapter с apply/undo в новой принадлежащей файловой копии и
fail-closed in-memory candidate для однозначных path-bytes решений и
квалифицированного слияния раздельных прямых Designer `Properties` с
сохранением исходных XML-фрагментов.
Workspace receipts получили строгую root/marker binding, legacy-политику и
Windows admission mutex, а BSL materializer и CLI bounded evidence закрывают
только квалифицированную область прямых `Properties`.
Исторические срезы выше не включали live apply. В текущем кандидате добавлен
отдельный bounded writer только для проверенного `rename_catalog_attribute` в
одном базовом `designer_xml` tree; это не native EDT/Конфигуратор writer и не
production deployment.

В дополнении 15 сентября identity evidence EDT доступны через dedicated
read-only [`edt-inventory`](EDT-INVENTORY-IDENTITY.md#local-cli) с явным
опубликованным snapshot, `project:read`, проверкой отзыва прав и ограничением
JSON 8 MiB. UUID, прямой XML-владелец и декларация слоя сохраняют partial
coverage; это не подтверждение типовой конфигурации или live compatibility.

Для трёх сохранённых inventory добавлен [EDT identity three-way plan](EDT-IDENTITY-THREE-WAY.md)
и read-only CLI `edt-inventory-plan`: проверенные bindings UUID/owner/layer,
явные конфликты и unsupported-причины, ограничение JSON 8 MiB. Это сравнение
предоставленного partial evidence без материализации или native validation.

## Дополнение к текущему публичному срезу

После исходного аудита scheduler получил durable journal/recovery и atomic
NotificationOutbox. Последующие hardening-коммиты устранили дублирование
фатальных уведомлений, ограничили вычисление backoff и удержание событий в
памяти. На текущем commit `e6bf91629807e236a7951e46c17a2bcc1ac72caf` локально
проходят 439 Python-тестов; Product CI завершился успешно в [main](https://github.com/DmitrL-dev/1cai-public/actions/runs/34711508531)
и [codex/edt-metadata-dev9](https://github.com/DmitrL-dev/1cai-public/actions/runs/34711512079).
Эти изменения укрепляют наблюдение, а текущий tree добавляет bounded HTTPS
webhook delivery с explicit ack; live metadata writer, SCM service и
подтверждение конкретного внешнего receiver-а остаются ограничениями ниже.

В кандидате `f7fb95ae` добавлены bounded foreground service-host для watcher-а,
retry allowlist и независимое сохранение fatal-ошибок, а также freshness-policy
runtime-метрик. Ранее в кандидате `909e3e5a` были добавлены bounded EDT identity inventory (UUID, прямой
XML-владелец, слой и `SourceRef`), атомарные companion scopes three-way для BSL,
форм и СКД, а также owner-report CLI. CLI требует реально опубликованный
snapshot, принимает только `<state-root>\owner-reports`, возвращает summary для
списка и учитывает размер JSON envelope для полной receipt. После финальной
reauth ошибки EDT identity не раскрывают source details при отзыве прав.
На том историческом срезе прошло 619 тестов, Black/Ruff, diff-check и
wheel/sdist build; native EDT/1С round-trip и фоновые service/notification/
Spectorn boundaries оставались непринятыми.

В следующем срезе UUID-aware planner добавил bounded evidence по прямым
свойствам Designer XML: для каждого изменённого свойства сохраняются только имя,
действие, SHA-256 и размер; независимые изменения помечаются
`disjoint_changes`, пересекающиеся — `overlap_conflict`. Это улучшает ревью,
но не является XML merge и не меняет консервативное действие объекта.

## Что уже имеет хорошую основу

- Источник истины находится в локальном core: проект, права, снимки, черновики,
  MCP и квитанции не делегируют контроль модели.
- Операции привязаны к snapshot/commit, ожидаемой ревизии и хэшам; конфликт и
  потеря ответа переводятся в явный результат, а повторная запись не делается
  автоматически.
- Metadata preview строит два полных diff и связывает candidate с сохранённым
  бизнес- и платформенным доказательством. Preflight apply проверяет свежесть,
  права и живые байты; отдельный bounded `designer_xml` writer делает запись
  только после этого preflight и проверяет CAS, backup, atomic replace,
  re-read и sealed receipt.
- Observer хранит Git-находки, события и квитанции транзакционно; replay,
  resolve и reopen переживают перезапуск. Bounded watcher повторно проверяет
  HEAD перед публикацией.
- Общий metadata reader теперь разбирает проверенные корневые EDT `.mdo` и
  bounded `.form`; смешение EDT и Designer-кандидатов отклоняется fail-closed.
- Появился файловый writer/undo с проверкой inventory и явным original/candidate recovery для отдельной принадлежащей workspace-копии; undo сохраняет проверенный backup и восстанавливается к original. Receipts state/recovery теперь привязаны к root/marker, старые журналы проходят узкую fail-closed policy, а OS lock и Windows identity-based admission mutex сериализуют mutation/recovery API; внешний concurrent CAS пока не обеспечен;
  live source и 1С остаются защищёнными от записи до native-квалификации.
- Поставлены bounded `GitWatcherScheduler` и read-only BSL-LS Git adapter;
  schema 3 дополнительно подготавливает принадлежащий snapshot доверенным
  локальным scanner, проверяет права/ancestry до capture и переиспользует
  matching owner receipts после рестарта. Анализ привязан к clean commit и
  повторной проверке HEAD, а неполный runtime результат не публикуется.
- Owner report теперь можно собрать из durable findings только при явной
  per-commit snapshot binding; исторический replay не меняет binding текущего
  состояния. Его можно сохранить в отдельный bounded store с immutable
  UUID receipt, эксклюзивным созданием и `fsync` с fail-closed обработкой
  частичной записи, а также повторной проверкой project/snapshot и прав при
  чтении; runtime adapter, physical retention reclaim и внешняя доставка остаются отдельными
  границами.
- Публичная поставка собирается офлайн, имеет MIT-лицензию, фиксированные
  хэши и явные ограничения. Основная рыночная позиция описана в
  [COMPETITOR-MATRIX.md](COMPETITOR-MATRIX.md).

Receiver evidence ограничен durable digest receipts. Локальные тесты проверяют
строгую схему и содержимое receipts, unsafe paths/sidecars, конкурентные повторы,
ошибки commit и потерю ответа между receiver и outbox с повторным открытием

power-loss и hostile filesystem mutation остаются отдельными непринятыми
границами; это дополнение не закрывает общую приёмку O1.

## Архитектурные решения

Граница ядра выбрана правильно для открытого продукта: модель является источником
предложения, а не полномочий; платформа 1С, BSL и тесты дают отдельные receipts.
SQLite и файловые хэши подходят для локального self-hosted профиля, если размеры,
срок хранения и восстановление после сбоя остаются явными.

Главный риск — преждевременно назвать bounded composition автономным агентом.
Schema 2 service entrypoint теперь собирает GitWatcherScheduler, read-only BSL,
durable findings/outbox и owner-report store с конечным бюджетом; это проверенный
локальный read-only цикл, но не live SCM daemon, внешний receiver или runtime
producer из 1С. Metadata gate остаётся read-only квалификацией, а bounded live
Designer XML writer работает отдельным явно вызванным контуром с sealed receipt.
Любой новый внешний процесс
должен получать project/snapshot binding и проходить повторную авторизацию перед
публикацией результата.

## Выбранное направление

Рентген позиционируется как полностью открытый MIT/self-hosted control plane
проверяемой разработки 1С. Существующие IDE, BSL LS, SonarQube, Vanessa, EDT MCP
и модели подключаются адаптерами. Собственная ценность — evidence-first lifecycle:
изменение, проверка, сохранение доработок при обновлении, постоянный аудит и
отчёт владельцу с источником каждой метрики. Это направление не требует
закрывать экосистему и позволяет подключить Spectorn как защищённый маршрут,
когда его локальный контракт будет принят.

## Порядок следующей работы

1. Связать native business-data evidence с live Designer XML writer/undo и
   отдельным recovery receipt; owned-copy и процессное прерывание уже приняты,
   остаётся проверка согласованного end-to-end статуса.
2. Принять schema 2/3 composition root на live SCM image/account/recovery и внешнем
   receiver с дедупликацией; затем подключить только доказательный runtime producer.
3. Начать three-way update на одной типовой конфигурации и зафиксировать
   матрицу совместимости, включая формы, СКД и расширения.
4. Подключить Spectorn по предоставленной инструкции и добавить negative-path
   acceptance без обхода защиты.
5. Только после этих доказательств поднимать версию и публиковать следующий
   prerelease; текущие dev8/0.1.8 теги остаются неизменными.
