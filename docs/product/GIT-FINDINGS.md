# Git evidence и жизненный цикл находок — библиотечный срез O1

Разработка в `codex/edt-metadata-dev9`, после опубликованного dev8.
`rentgen_core/git_observer.py` предоставляет probe и чистую reconciliation-
функцию, а `rentgen_core/git_watcher.py` связывает их с observer. SQLite
observer хранит state/events/receipts атомарно; `record-findings` и
`findings-status` доступны через CLI. Это принятый bounded срез направления 4
из [ROADMAP](../../ROADMAP.md). [READINESS](READINESS.md) по-прежнему не
утверждает готовность фонового scheduler, поставляемого analyzer или общей
приёмки O1.

## Наблюдение за Git

`observe_git` принимает корень локального рабочего дерева и возвращает
канонический локальный путь, полный commit HEAD и symbolic ref либо `None`
для detached HEAD. Поддерживается Git worktree с `.git`-файлом. Повторный вызов
при том же состоянии возвращает равное значение; потребитель может использовать
его вместе с профилем анализатора и scope как ключ повторного использования.

Probe читает HEAD/ref до и после проверки tracked-файлов. Он отказывает при
изменениях tracked-файлов в индексе или рабочем дереве, заметной смене HEAD/ref,
неинициализированном HEAD, передаче подкаталога, ошибке Git и превышении
10 секунд отдельной команды. Git запускается без shell, pager, внешнего diff,
textconv, fsmonitor и интерактивных запросов. Наследованные `GIT_*` переменные
не могут перенаправить probe на другой репозиторий; lazy fetch отключён.
Нет fetch/pull, изменения refs, создания commit, запуска анализатора или LLM.

**Область — закоммиченные файлы.** Untracked/ignored-файлы не входят в неё.
Результат не удостоверяет байты живой выгрузки. Между чтениями возможны
изменения и возврат прежнего состояния; атомарность probe не заявляется.
Для диагностики потребитель обязан читать именно immutable commit и сохранять
его связь с отчётом, а не анализировать случайное состояние рабочего каталога.
Git и локальная конфигурация репозитория предполагаются доверенными.

## Контракт отчёта и переходы

`FindingReport` содержит `GitObservation`, `profile_id`, `scope_id`, явный
`complete=True` и tuple находок. Профиль должен идентифицировать конкретные
версию анализатора, правила и настройки; scope — одинаковую полную область
проверки. Например, для изолированной диагностики одного модуля нужен scope
именно этого модуля. Частичный отчёт, сбой анализатора и усечённый список нельзя
передавать как полный успешный отчёт.

`Finding` содержит rule, канонический относительный POSIX path, anchor,
message и номер строки от 1. Идентичность — `(rule, path, anchor)`; текст
сообщения и строка в неё не входят. Anchor задаёт адаптер анализатора, он должен
устойчиво различать несколько одинаковых правил внутри файла. Этот модуль не
вычисляет AST anchors и не угадывает соответствие неоднозначных находок.
Дубликаты идентичности вызывают отказ; перемещение файла означает другую
идентичность, автоматического сопоставления переименований пока нет.

| Вход | Результат |
| --- | --- |
| Первый полный отчёт | Baseline, событие `new` для каждой находки |
| Тот же commit/context и эквивалентный отчёт | Прежнее состояние, событий нет |
| Тот же commit/context и другой отчёт | Явный конфликт replay |
| Находка снова присутствует в следующем отчёте | Обновляется `last_seen` и текст/строка, нового события нет |
| Открытая находка отсутствует в полном отчёте | Событие `resolved`, устанавливается `resolved_at` |
| Закрытая находка снова появилась | Событие `reopened`, сохраняется `first_seen` |
| Закрытая находка по-прежнему отсутствует | Состояние закрытия сохраняется, событий нет |
| Другой repository/ref/profile/scope | Отказ; нужен отдельный baseline |
| Неполный отчёт | Отказ без изменения прежнего состояния |

`first_seen`, `last_seen` и `resolved_at` — commit IDs. Это последовательность
наблюдений вызывающей стороны; проверка ancestry, force push и сортировка по
времени не выполняются. Detached HEAD представляет отдельный контекст.
Смена профиля/ветки не должна автоматически закрывать прежние находки.

Результат — immutable `FindingUpdate(state, events)`. Выход сортируется по
идентичности, поэтому порядок входных диагностик не влияет на результат.
Закрытые записи сохраняются для последующего reopen. По умолчанию предел
10 000 уникальных записей, включая закрытые; при превышении функция отказывает,
а не удаляет историю. Текстовые поля находки ограничены 4096 символами каждое.

Конструкторы DTO и `complete=True` не являются доказательством запуска
анализатора. Функция принимает типизированные данные доверенного адаптера,
а не произвольный JSON клиента. Проверка прав, provenance и существующих
сохранённых состояний должна выполняться будущим application use case.

## Следующий этап и границы проверки

Для production watcher необходимо отдельно реализовать разрешённый проектный
профиль и политику Git, анализ immutable commit, достоверные anchors, ключ
повторного использования результатов, scheduler и уведомления. Нужно
согласовать восстановление после сбоя, конкуренцию, branch rewrite, ancestry и
очистку истории. Текущий watcher не запускает analyzer, не создаёт фонового
процесса и не заменяет общую диагностику конфигурации или бизнес-метрики.

Проверки `tests/unit/test_git_observer.py` используют временные настоящие
локальные репозитории для baseline, нового commit, staged/unstaged изменений,
worktree и detached HEAD. Гонка HEAD и timeout моделируются отдельно.
Lifecycle проверяется детерминированными полными/неполными отчётами, включая
replay, resolve/reopen, разделение контекстов, дубликаты и лимит истории.
Это регрессионная проверка probe/reconciliation на Windows/Python 3.11 с
временными Git-репозиториями и caller-supplied отчётами; она не заменяет
приёмку реального analyzer, типовой конфигурации 1С и фонового scheduler.

```powershell
python -m pytest tests/unit/test_git_observer.py tests/unit/test_source_observer.py -q
python -m ruff check rentgen_core/git_observer.py tests/unit/test_git_observer.py
python -m black --check rentgen_core/git_observer.py tests/unit/test_git_observer.py
```
