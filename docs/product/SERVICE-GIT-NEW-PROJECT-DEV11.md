# Core dev11: новый проект и первый холодный цикл GitAuditWorker

25 сентября 2026 года по местному времени проверен **полный** `Rentgen.GitAudit`
schema 2 в console mode на установленном публичном Core `0.1.0.dev11`.
Для первичной серии созданы девять отдельных собственных синтетических
Git-проектов с одним BSL-модулем, девять новых observer-профилей и девять
новых установок runtime. Для каждого
проекта публичные `rentgen registry-init` / `project-register`,
`rentgen-observer init` / `run` предшествовали первому worker-циклу. JDK каждый
раз заново распаковывался из одного закреплённого официального ZIP и
устанавливался публичным `install_bsl_runtime.py`; installer подтвердил
`installed` и 490 файлов JDK.

Первый **публичный** цикл проекта №1 завершился безопасным отказом. Повторный
цикл без переустановки runtime дал `analyzed`. Это новая отрицательная проба
на свежей регистрации проекта, дополняющая прежние отрицательные пробы из
[issue #23](https://github.com/DmitrL-dev/1cai-public/issues/23). Внутренний
`reason` именно этого отказа не был записан, поэтому ему **не** присваивается
код `BSL_INPUT_CHANGED` по аналогии с прежними случаями.

## Наблюдение первого проекта

Новая регистрация проекта №1: commit
`927926030018b3d997712f8aed3d1271ed4fbdd8`, опубликованный snapshot
`96768925e6c933922167a1dec80c4c1d35b06941eaf3cf27e9315a9cf9deebd8`.
До первого запуска outbox отсутствовал. `rentgen-service.exe --console` вернул
exit `2`, снаружи `SERVICE_WORKER_FAILED`. Журнал остался на `cycle=0` и
`GIT_ANALYZER_INCOMPLETE`/`fatal`; единственная запись outbox была `fatal` без
`owner_report_id`. Успешного owner report этот цикл не создал. При этом в
сохранённом diagnostic scratch настоящий BSL-LS успел записать `bsl-json.json`
с diagnostic `MagicNumber` (SHA256
`50e5d9519dd25dd71698cf692cf52750c00e33ddb2b46a43add0ab096c819c98`).
Наличие файла отчёта само по себе не подтверждает завершённую проверку runtime.

Повтор `rentgen-service.exe --console` с **теми же** runtime, commit и snapshot
вернул exit `0`, `cycles=1`: первые два события outbox стали `fatal`, затем
`analyzed`. Публичный `rentgen owner-report-get` прочитал новый отчёт с
`quality.status=available`, `git_source_verified`, привязкой к тому же commit
и snapshot и одним `bsl/MagicNumber` finding. Исходный Git-проект сохранился.
Позднее для отдельной диагностической пробы создан второй собственный commit;
его нельзя путать с исходником первого отказа.

`Get-Item` показал одинаковый базовый `LastWriteTimeUtc` каталогов JDK `conf`,
`lib`, `jmods` до и после первого отказа. Это **не** проверка полного
`FileStamp`/инвентаря и не опровергает ранее зафиксированное изменение
`write`/`change` в другой холодной пробе. Внутренний результат
`InstalledDiagnostics.analyze` при этом первом отказе не сохранялся.
Системная трассировка `Microsoft-Windows-Kernel-File` и чтение полной ленты
USN ответили `Access is denied` без прав администратора; `usn readdata`
отдельных объектов не устанавливает процесс, изменивший метаданные.

## Отдельные контроли

| Сценарий | Первый цикл | Доказательство |
| --- | --- | --- |
| Новый commit того же проекта, новый runtime, диагностический hook | `completed`, `runtime_verified=true`, `diagnostics_complete=true`, exit `0` | Новый snapshot; hook SHA256 `c890402c69a43d19e94c55816c754c4f0d441f1c214c06975ee461d1907d0ce9` |
| Шесть иных новых регистраций, каждая со свежим runtime (проекты №2–7) | Шесть `analyzed`, по одному настоящему `bsl/MagicNumber` finding | Hook подтвердил `completed`/`runtime_verified`/`diagnostics_complete`; публичный `owner-report-get` подтвердил `git_source_verified` |
| Две иные новые регистрации без hook (проекты №8–9) | Два публичных `rentgen-service.exe --console`: exit `0`, `cycles=1`, `analyzed` | Публичный `owner-report-get`: по одному `bsl/MagicNumber`, `git_source_verified` |

Hook оборачивает методы только в **локальном диагностическом процессе** и
пишет внутренний результат после вызова. Он заранее импортирует модули и
может изменить тайминг. Поэтому семь его успешных циклов отделены от двух
контрольных запусков обычного публичного CLI и не рассматриваются как
исправление. В каждой из восьми других регистраций опубликован собственный
snapshot, JAR сохранил закреплённый SHA256, outbox содержит одно `analyzed`,
owner report привязан к своему commit/snapshot, исходное дерево чистое.

## Квитанция и граница приёмки

[Машинная ограниченная квитанция](evidence/service-git-new-project-dev11-20260925.json)
имеет SHA256
`f4671e88f21a09957333557481b7d1ea186ab0e3f51699ebd377bd0ac869f427`.
Она содержит синтетические идентификаторы, SHA256 локальных config/outbox,
сохранённых отчётов и probe, результаты по проектам и пределы проверки. Сами
логи и каталоги с путями хоста остаются вне Git; квитанция не содержит пути
хоста или SID.

Итог ограничен: первый отказ полного worker **воспроизведён и после новой
регистрации проекта**; последующие успехи показывают его непостоянство, но
причина этого отказа и его связь с прежним внутренним `BSL_INPUT_CHANGED` не
установлены. [Issue #23](https://github.com/DmitrL-dev/1cai-public/issues/23)
и холодная приёмка остаются открытыми. Для решения нужна трасса полного
инвентаря и файловой активности **во время** следующего отказа, а затем
отдельная проверка намеренной мутации JDK/JAR с прежним fail-closed
поведением. На этом хосте системная трасса требует административных прав.
Второй Windows-хост, service account/SCM, внешний конкурентный writer,
типовые `.cf/.cfe`, рабочая ИБ, публичный HTTPS/DNS и production deployment
здесь не проверялись. Код, бинарники, tag и вложения Core dev11 не менялись.
