# Управляемая правка через локальную модель

2026-09-10. Реализован CLI в development checkout поверх установленного core
`0.1.0.dev7` / MCP `1.30.0`. В текущий ZIP ядра эти скрипты не входят;
companion 0.1.4 включает их в VSIX и добавляет запуск из дерева модулей.
Собственный код MIT. [Команды редактора](../../integrations/vscode-rentgen/README.md).

Подготовьте обычный профиль редактора, установленную локальную модель Ollama
и закреплённый runtime BSL. Из `source-list` сохраните точный объект `entry.ref`
выбранного модуля в JSON; инструкцию сохраните в UTF-8 без BOM. Запускайте Python
из профиля, а не системный интерпретатор:

```powershell
& 'C:\Rentgen\environment\Scripts\python.exe' -I `
  'C:\Rentgen-source\integrations\open-editor\run_repair.py' `
  --profile 'C:\Rentgen\editor-profile' `
  --source-ref 'C:\Rentgen\selected-source-ref.json' `
  --instruction 'C:\Rentgen\instruction.txt' `
  --output 'C:\Rentgen\runs\new-run' `
  --model 'qwen3.5:9b'
```

Пути — пример, замените их на подготовленные каталоги. `--think` включает
рассуждение у поддерживающей его модели; лимиты остаются прежними. Ollama
должна слушать `http://127.0.0.1:11434`; загрузку модели адаптер не выполняет.
Наличие локального endpoint само по себе не гарантирует отсутствие дальнейшей
передачи внутри выбранного сервера/модели. Spectorn здесь ещё не подключён.

Запуск создаёт новый сохранённый черновик, проверяет исходную ревизию,
запрашивает одну правку и проверяет сохранённую новую ревизию. Модель не выбирает
инструменты, проект, пути или ID операций. Исходный файл не изменяется.
Возвращаемые замены должны совпадать точно, быть уникальными и не пересекаться.
BOM и исходные LF/CRLF сохраняются. Полный модуль ограничен 32 КиБ; при превышении
адаптер останавливается без усечения. Инструкция — до 4 КиБ. Один запрос модели
ограничен 120 секундами и 4096 выходными токенами; общий срок — 420 секунд.

Каталог результата должен быть новым. В `events.jsonl` журналируются фазы,
квитанции и ID операций; намерение записи сбрасывается на диск до её отправки.
`result.json` содержит фактический результат и связанные диагностики. Код
возврата 0 означает `analysis_clean`, 1 — диагностики или отказ. Даже
`analysis_clean` не доказывает соответствие бизнес-требованию. Историю и diff
нужно просмотреть; тесты 1С не запускались, применения нет.

В `model-proposal.json.txt` сохраняется ограниченный исходный ответ с предложенной
правкой, в том числе при ошибке его разбора. Файл может содержать код модуля;
он остаётся в выбранном каталоге запуска. Исходный запрос и отдельное поле
рассуждения модели туда не записываются. Парсер принимает объект JSON или один
цельный Markdown-блок `json`. Текст вокруг блока, несколько блоков, повторные
ключи, лишние поля и неоднозначные замены отклоняются. Ошибка JSON получает
стабильный код `MODEL_INVALID_JSON`, тип исключения также попадает в журнал.

После потери ответа не запускайте тот же запрос заново вслепую. Прочитайте
`draft-receipt --operation-id UUID` из журнала через CLI выбранного профиля;
отсутствие ответа не означает отсутствия записи. Автоматического повторения
модельного запроса или мутации в адаптере нет. Новый запуск создаст другой
черновик. Companion 0.1.4 предоставляет команду проверки прежнего результата
по квитанциям, в том числе после перезапуска редактора.

## Реальные результаты

Попытки использовали искусственный модуль `СохранитьДокумент`, подавляющий
ошибку в пустом блоке исключения. До изменения настоящий BSL LS нашёл
`MissingCodeTryCatchEx`. Два первоначальных результата 4B не приняты как исправление.

| Режим Qwen3.5:4b | Наблюдение | Приёмка |
|---|---|---|
| Без рассуждения | Один запрос: 511 входных / 155 выходных токенов, 3191 байт; модель около 6,22 с. Записана ревизия 2 с `Сообщить`, ошибка по-прежнему подавляется; новый `DeprecatedMessage` | Отрицательная: неверный смысл и диагностика |
| С `--think` | Ответ отклонён как `MODEL_INCOMPLETE_RESPONSE` до отправки правки; сохранилась только ревизия 1 | Отрицательная: завершённой правки нет |

Для второй попытки конкретное поле, вызвавшее отказ, и счётчики ответа не были
сохранены старой обработкой ошибок. Нельзя утверждать, что причиной был именно
лимит токенов. После проверки добавлены ограниченные метаданные отказов:
счётчики, `done_reason`, размер и хеш ответа, без исходника и текста рассуждения.
На этапе 4B этот журнал проверен HTTP-тестом без новой генерации.

На следующем этапе проверена уже установленная **Qwen3.5:9b без рассуждения**.
Первый полный прогон остановился до правки с общей ошибкой обработки. Отдельный
захват одного ответа модели без MCP/BSL установил причину: завершённый ответ
содержит правильный объект в Markdown-блоке json. Добавлена поддержка именно
такой цельной оболочки, все проверки содержимого сохранены. Первые отрицательные
отчёты не переписаны задним числом.

После изменения парсера новый полный прогон и независимая проверка **приняты**:
один запрос, 511 входных / 148 выходных токенов, 3191 байт запроса; генерация
около 16,52 с, цикл создания/анализа/правки/повторного анализа около 42,17 с.
Сохранена ревизия 2 с `Raise;` в обработчике; повторный и отдельный CLI-анализы
чисты. Исходный файл и head не изменились, квитанции совпали с журналом.
В этом этапе всего три модельных запроса: первоначальный прогон, захват ответа
без записи и новый прогон после исправления парсера. Внутренних автоповторов нет.

`Raise;` внутри обработчика передаёт исключение вышестоящему обработчику —
это поддерживаемый английский синтаксис, описанный в
[руководстве 1Ci, 4.6.10.3](https://kb.1ci.com/1C_Enterprise_Platform/Guides/Developer_Guides/1C_Enterprise_8.3.23_Developer_Guide/Chapter_4._1C_Enterprise_language/4.6._Statements_and_syntax_structures/4.6.10._Operations_with_exceptions/).
Политика искусственного примера теперь принимает оба написания оператора без
аргументов. Подмена исключения сообщением или другим исключением не допускается.
Это устранение ложного отказа по языку, а не изменение бизнес-требования.

Независимый CLI подтвердил квитанции, ревизии, неизменные исходник/head.
Проверка смысла выполнена отдельной политикой именно этого искусственного
примера. Первая попытка прошла весь технический цикл анализа/сохранения,
но это не означает качественной AI-разработки. Положительный пример 9B также
не доказывает качество произвольных задач или работу в платформе 1С.
Команда, просмотр результата и восстановление в companion 0.1.4 проверены
отдельным прогоном и новой сессией редактора; см.
[свидетельства редакторного сценария](EDITOR-REPAIR-ACCEPTANCE.md).
Далее требуется расширение набора содержательных сценариев.

Свидетельства в `C:/1cAI/output/product-readiness-2026-09-08`:
`editor-managed-repair-attempt-20260910.json` и
`editor-managed-repair-thinking-attempt-20260910.json`. Скрипт независимой
проверки: `scripts/verification/verify_managed_repair.py`.

Положительная приёмка: `editor-managed-repair-9b-accepted-20260910.json`;
сводка этапа: `managed-repair-9b-checkpoint.json` в том же каталоге свидетельств.
Захваченный при диагностике и принятый после исправления ответы модели совпали
байт в байт. Промпт и требования между ними не менялись.
