## Изменение проверщика

Новый `process_inspection` выполняет не более трёх полных WMI опросов на одну
попытку получить снимок. Повтор разрешён только при корректной структуре строк
с `null` или пустой строкой в image/argv. Все строки проверяются до решения о
повторе: ранний `null` не скрывает повреждённую последующую строку.

Каждый capture сохраняется под новым последовательным именем. Неполный снимок
получает `stock_process_inventory_observed` с `complete=false`; после восстановления
привилегий записывается `stock_process_inventory_retry`. Полный снимок получает
`complete=true`. Неполные строки не передаются проверкам Java или отсутствия
потомков. Третья неполная попытка завершает проверку отказом.

Ошибки захвата, timeout, overflow, незавершённый child, неверные типы/ключи,
повторные PID и нарушение общего бюджета завершают проверку сразу. Сохраняются
пределы 200 опросов на полный lifecycle, 100 строк, 10 секунд на capture и
32768 байт на поток. Timeout capture ограничивается оставшимся общим бюджетом.

Каждый опрос получает отдельную временную область `SeDebugPrivilege` и точное
восстановление исходного состояния. Проверка пути и токена Java выполняется
внутри области последнего полного снимка. Microsoft описывает требуемую
привилегию у свойства [Win32_Process.ExecutablePath](https://learn.microsoft.com/en-us/windows/win32/cimwin32prov/win32-process).
Сам локальный запрос, флаг16, Count/ItemIndex и его SHA остаются прежними.

Новый вариант повторяет только чтение процессов проверщиком. SCM lifetimes,
анализатор, операторские commits, порядок STOP/recovery/refusal и публикации
не повторяются этим механизмом. Удержанный объект службы и правила cleanup
сохраняются. Производственные модули Core этим исправлением не изменены.

## Условия приёмки следующего кандидата

Следующий exact source должен пройти оба исходных push/PR attempt1 с 2968 Python,
71 Companion, двумя группами Go, 723 локальными идентификаторами и 105 собственными
файлами wheel. Обязательны отдельные SourceObserver и Git diagnostic доказательства
и все пять групп полного stock сценария:

1. Первый холодный Git/BSL анализ с настоящим Java и полной durable публикацией.
2. Операторский commit только при STOPPED и второй полный Git/BSL анализ.
3. Неизменённая голова, штатный STOP, завершение исходного удержанного объекта,
   отсутствие потомков/lease и повторной публикации.
4. Прерывание quiet wait, отказ restart, явное recovery и неизменённая голова.
5. Refusal переписанной истории до capture и отказ при утрате прав LocalService
   с восстановлением исходного состояния.

Пределы приёмки: пять positive lifetimes, 14 controls, два реальных Java,
три свежих отказа, restoration owners/DACL/privileges и полные retained SQLite/JSON.
Проверка активного BSL interruption в этот сценарий не входит. Успешный повторный
опрос не заменяет ни одну из этих групп и не гарантирует, что короткое Java окно
будет поймано: без его фактического доказательства результат останется отказом.

После успешного source CI нужны квалификация точного merged main, новая offline
установка, проверка editor/SDK и immutable component assets. Core tag должен
указывать на embedded source commit C; release records — на последующий commit R;
Companion tag — на R. Затем публикуются releases и подробный анонс с readback.
Текущий публичный accepted main и принятые releases dev15 сохраняют свою
историческую квалификацию. Установка dev16, выпуск dev16 и production deployment
этой локальной проверкой не подтверждены.
