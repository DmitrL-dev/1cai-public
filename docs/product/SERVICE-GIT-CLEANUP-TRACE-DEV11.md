# Core dev11: трасса прерывистого отказа холодного Git audit при очистке

25 сентября 2026 года на одном Windows-хосте я продолжил первый полный цикл
`Rentgen.GitAudit` schema 2 в console mode. Каждый проект создавался заново с
одним собственным синтетическим `.bsl`-модулем, отдельными регистрацией,
observer snapshot и профилем. Закреплённый Temurin 21.0.12.1+1 каждый раз
распаковывался из ZIP SHA256
`f9d6e191ab098c0d416e7d588a24420a8621cd2f4720dab2459b8b7b2d2d8b4e`;
публичный installer устанавливал 490 файлов JDK и BSL Language Server 1.0.5
JAR SHA256
`de97f571e6474c5c151cf859294f589ee01152de3b4826b43e1a80b69ee2602a`.
Это дополнение к [первой серии новых проектов](SERVICE-GIT-NEW-PROJECT-DEV11.md)
и [issue #23](https://github.com/DmitrL-dev/1cai-public/issues/23).

## Разделение публичного запуска и локальной диагностики

Прогон №14 использовал **обычный установленный Core dev11 без hook**. Первый
worker вернул exit `2`, журнал `GIT_ANALYZER_INCOMPLETE`/`fatal`, outbox содержал
только `fatal`, owner report отсутствовал. Внутренний `reason` этого прогона
не записан. Git commit и observer snapshot сохранены в
[машинной квитанции](evidence/service-git-cleanup-trace-dev11-20260925.json).

Прогоны №20, 25, 26, 29 и 42 использовали локальную диагностическую копию
Python-пакета через `PYTHONPATH` **только в процессе worker**. Копия добавляла
запись внутреннего `BslAnalysis`, этапов очистки и повторные чтения
в момент уже возникшего отказа. Установленный пакет dev11,
публичный installer и исходники репозитория остались без изменений; SHA256
трёх проверенных установленных модулей совпали с текущим исходным деревом.
Диагностическая копия могла изменить тайминг, поэтому её внутренний код нельзя
автоматически переносить на №14 или первоначальный отказ из issue #23.

| Прогон | Наблюдение первого worker |
| --- | --- |
| №20 | `BSL_CLEANUP_FAILED`, Java exit `0`, `runtime_verified=true`, отчёт сформирован; снаружи exit `2` / `fatal` |
| №25 | Тот же внутренний код, этап `_cleanup` → `delete_attempt` |
| №26 | Проверка пустоты корня собственного scratch attempt отказала; после выхода worker свежий просмотр увидел пустой корень |
| №29 | В каталоге кеша BSL-LS первое, повторное и новое перечисления увидели один `offheap-disk-store` с одинаковой идентичностью; после выхода worker он исчез |
| №42 | Первый список каталога кеша содержал запись по пути ранее помеченного на удаление потомка; немедленные повторное и новое перечисления были пустыми, новое открытие пути вернуло WinError `2` (`FILE_NOT_FOUND`) |

В №42 диагностическая трасса подтверждает, что до проверки родителя
объект под этим путём прошёл `delete_verified`: дескриптор был открыт без следования
ссылкам, его идентичность сверена с ранее закреплённым объектом и
`SetFileInformationByHandle(FileDispositionInfo)` вернул успех. В первом
перечислении родителя ещё была запись под тем же именем. Трасса не сравнила
идентичность этой записи с объектом, ранее помеченным на удаление. Во втором
перечислении того же дескриптора и в перечислении нового дескриптора записей
уже не было; новое открытие пути завершилось WinError `2`. После выхода
worker родитель существовал и был пуст. Такой исход согласуется с
**кратковременным расхождением наблюдений очистки**, но не исключает
создание новой записи под тем же именем между проверками. Трасса №29 не
позволяет свести все отказы к устаревшему одному дескриптору: три
перечисления тогда видели потомка.

[Документация Microsoft по `SetFileInformationByHandle`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle)
описывает постановку объекта на удаление;
[`FILE_STANDARD_INFO.DeletePending`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_standard_info)
показывает состояние очереди удаления. В этих прогонах `DeletePending` не
снимался, а файловая ETW/полная лента USN без администратора недоступны.
Поэтому точный механизм задержки, наличие внешнего писателя и причина
**первоначального** `BSL_INPUT_CHANGED` остаются неустановленными.

## Контроли и отдельный сбой установки

Новые первые циклы №36 и №38–41 с тем же диагностическим слоем завершились
exit `0`, событием `analyzed` и чистыми Git-деревьями. Серия была ограничена
первым отказом №42. Отдельный №37 остановился **до worker**: публичный installer
после копирования и проверки staging-дерева получил `PermissionError` /
WinError `5` на `stage.rename(target)`. Повтор того же installer спустя минуту
подтвердил `installed` и 490 файлов; worker №37 не запускался. Это отдельный
прерывистый отказ публикации runtime, причина WinError `5` не установлена.

Перед и после каждого из одиннадцати перечисленных в квитанции worker-циклов
снимались полные Win32 FileStamp **579 установленных объектов runtime**.
Соответствующие JSON-снимки совпали побайтно, включая все пять отрицательных
диагностических циклов и публичный №14. Это исключает только сохраняющееся
изменение между снимками; кратковременную мутацию во время worker, ошибку
тайминга или внешнего писателя такие снимки не исключают. Во всех этих циклах
исходные Git-деревья остались чистыми. При отрицательных исходах успешный
owner report не публиковался.

## Публичная квитанция и граница решения

[Машинная квитанция](evidence/service-git-cleanup-trace-dev11-20260925.json)
SHA256 `e3ee39c1d67854433329c63f1cf333b4e33240f922ca28877fb1324bcb365211`
содержит commit/snapshot, SHA256 полных снимков runtime и локальных трасс,
способ каждого запуска, результаты worker и ограниченные относительные факты
трасс №29/42. Сами логи с локальными путями и SID не публикуются.

Перед изменением продуктовой логики требуется проверить, что остающийся
потомок ранее прошёл `delete_verified` с прежней идентичностью, и ограниченно
дождаться согласования перечисления с фактическим удалением. Неизвестный или
изменённый объект, истечение времени и неопределённая очистка должны
сохранять fail-closed. Отдельные тесты должны доказать отрицательные случаи
и нативный первый цикл. Это пока направление проверки, **не реализованное
исправление**. Issue #23 и холодная приёмка Core dev11 остаются открытыми.
Второй Windows-хост, service account/SCM, типовые `.cf/.cfe`, живая ИБ,
HTTPS/DNS и production deployment этим опытом не приняты. Tag и вложения Core
dev11, продуктовый код и бинарники не менялись.
