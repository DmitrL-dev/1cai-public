# 🧭 AI Scenario Hub & Two-Contour Execution (Reference)

> Статус: экспериментальный reference-документ (не production-обещание).  
> Цель: описать, как поверх текущего Orchestrator/агентов/DR можно
> построить слой сценариев, двухконтурный режим и доверие к действиям.

---

## 1. Задача, которую решает Scenario Hub

Сейчас в платформе есть:

- AI Orchestrator (`src/ai/orchestrator.py`),
- BA / Dev / QA / DevOps агенты,
- DR rehearsal и постмортемы,
- Deno execution environment для безопасного исполнения кода.

Проблема: пользователю сложно видеть это как **целостные сценарии** —
получается «зоопарк инструментов» и протоколов (HTTP, MCP, скрипты).

**Scenario Hub** предлагает оперировать:

- **целями** (goals) на языке пользователя;
- **сценариями** (scenarios), которые описывают путь к цели;
- **плейбуками** (plans) для детерминированного выполнения сценариев;
- **уровнем риска и автономности** для каждого шага;
- **оценкой доверия (trust-score)** к сценариям и их результатам.

---

## 2. Двухконтурный режим: online планирование и offline выполнение

### Online-контур (планирование)

- BA / Dev / QA / DevOps агенты и Orchestrator работают с пользователем,
  чтобы:
  - понять цель (ScenarioGoal),
  - уточнить ограничения и критерии успеха,
  - предложить **ScenarioPlan** из шагов (ScenarioStep).
- MCP/LLM здесь используются для размышлений, диалога и генерации плана.

### Offline-контур (выполнение)

- После утверждения плана человеком:
  - выполнение уезжает в offline-контур (плейбуки / execution-env / HTTP API),
  - **LLM и MCP не участвуют в рантайме**, план детерминирован,
  - безопасность и надёжность обеспечиваются тестами, полиси и DR-практиками.

В результате:

- онлайн-контур даёт гибкость и «умных» помощников;
- офлайн-контур даёт предсказуемость и повторяемость.

## 3. Примеры сценариев и планы (реализовано как типы)

В `src/ai/scenario_hub.py` описаны базовые модели:

- `ScenarioGoal` — цель сценария: id, заголовок, описание, ограничения,
  критерии успеха.
- `ScenarioStep` — один шаг: риск, требуемый уровень автономности,
  исполнитель (`executor`), формальные проверки (`checks`) и metadata.
- `ScenarioPlan` — детерминированный план: список шагов, общий риск,
  требуемый уровень автономности (`AutonomyLevel`).
- `ScenarioRiskLevel` — шкала риск-профиля: read-only, non-prod, prod-low,
  prod-high.
- `AutonomyLevel` — уровни автономности системы (A0–A3).

Примерные сценарии, реализованные в коде и плейбуках, находятся в:

- `src/ai/scenario_examples.py`:
  - `example_ba_dev_qa_scenario(feature_id)` — BA→Dev→QA;
  - `example_dr_rehearsal_scenario(service_name)` — DR rehearsal для сервиса;
  - `example_code_review_scenario(feature_id)` — code review для фичи/PR;
- `playbooks/ba_dev_qa_example.yaml` — YAML‑плейбук BA→Dev→QA;
- `playbooks/dr_vault_example.yaml` — YAML‑плейбук DR rehearsal;
- `playbooks/security_audit_example.yaml` — YAML‑плейбук security-audit;
- `playbooks/code_review_pr_example.yaml` — YAML‑плейбук code review PR.

На этом этапе модели не «подключены» к FastAPI/Orchestrator — это
reference-слой типов, который можно использовать:

- в новых API (например, `/api/scenarios/plan`, `/api/scenarios/execute`),
- в BA/Dev/QA/DevOps гайдах и e2e-тестах,
- в DR rehearsal и security playbooks.

## 4. Оркестратор, уровни автономности и риск

Вместо одного флага "есть approval / нет" планируется:

- глобальный **уровень автономности** для инсталляции/окружения:
  - `A0_propose_only` — только предложения и отчёты;
  - `A1_safe_automation` — низкорисковые сценарии (read-only, non-prod);
  - `A2_non_prod_changes` — изменения в test/staging;
  - `A3_restricted_prod` — ограниченные действия в prod по строгим плейбукам.
- у каждого `ScenarioStep` — свой `risk_level` и `autonomy_required`.

Идея: Orchestrator (и/или DevOps-агент) проверяет, можно ли выполнять
конкретный шаг в текущем уровне автономности:

- если нет — шаг всегда требует ручного approval или запускается
  только в более «сильных» окружениях;
- если да — можно использовать полностью автоматический режим.

## 5. Trust Score и отчёты для пользователя

Чтобы сценарии были **понятны** и вызывали доверие, вводится:

- `TrustScore` — числовая оценка (0–1) + уровень ("low"/"medium"/"high")
  и список причин;
- `ScenarioExecutionReport` — краткий нарративный отчёт:
  - цель, план, уровень доверия до и после;
  - временная шкала ключевых событий;
  - ссылки на артефакты (логи, постмортемы, ADR, отчёты).

В `compute_trust_score(...)` реализована простая эвристика:

- тесты проходят / не проходят;
- покрытие тестами выше / ниже порога;
- есть ли недавние инциденты;
- какой риск у сценария (read-only vs prod-high).

Эта функция — **заглушка/референс**. Её задача — показать, как
можно технически привязать «ощущение доверия» к объективным
метрикам (тесты, инциденты, риск), а не к чисто субъективному мнению.

---

## 6. Как это соотносится с текущим стеком

Кратко:

- **BA / Dev / QA / DevOps** — остаются основными ролями/агентами,
  но теперь работают через сценарии и планы.
- **AI Orchestrator** — вместо прямых вызовов инструментов может:
  - помогать планировать сценарии (online-контур),
  - запускать/мониторить плейбуки (offline-контур).
- **Execution Environment (Deno)** — становится основным исполнителем
  шагов плейбуков, особенно для тяжёлых и рискованных операций.
- **MCP** — рассматривается как один из протоколов, а не как ядро:
  его можно подключать для IDE/интерактива, но основной runtime
  сценариев может работать через HTTP/skills/плейбуки без MCP.

## 7. Следующие шаги (дорожная карта)

Набросок возможных следующих шагов (необязательных, зависит от приоритетов):

1. Добавить экспериментальный API `GET /api/scenarios/examples`,
   который возвращает несколько примерных `ScenarioPlan` (BA→Dev→QA,
   DR rehearsal, security-audit). Базовые примеры уже описаны
   в `src/ai/scenario_examples.py`, а endpoint реализован в
   `src/ai/orchestrator.py` (read-only, experimental).
2. Описать ключевые сценарии в виде YAML/JSON-плейбуков и связать их
   с существующими скриптами (`scripts/runbooks/*`, security-audit).
   Базовые YAML-плейбуки добавлены в
   `playbooks/ba_dev_qa_example.yaml`,
   `playbooks/dr_vault_example.yaml`
   и `playbooks/security_audit_example.yaml`, dry-run исполнитель
   реализован в `src/ai/playbook_executor.py` и
   `scripts/runbooks/run_playbook.py`
   (поддерживаются уровни автономности и применение Scenario Policy).
3. Внедрить расчёт `TrustScore` в отчёты DR/postmortem (как поле
   «уровень доверия к сценарию до/после»).
4. В отдельной ADR зафиксировать уровни автономности и политики,
   чтобы было понятно, какие действия разрешены на каждом уровне.

Этот документ не меняет поведение прод-кода, но задаёт рамку, куда
можно развивать Orchestrator и агентов, чтобы они были:

- интересными (агент как партнёр по сценарию, а не только tool-caller),
- надёжными и безопасными (двухконтурный режим, risk/AutonomyLevel),
- функциональными (плейбуки, exec-env, DR/BA/Dev/QA),
- понятными пользователю (цели, планы, trust-score и отчёты).
